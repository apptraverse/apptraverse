## 1. Назначение и граница продукта

AppTraverse — библиотечная основа для приложений с сохраняемым объектным состоянием, частичной загрузкой графа, типизированными изменениями и независимыми представлениями для разных платформ. Библиотека не определяет бизнес-модель потребителя, его корневой класс, число экранов или идентификатор корня. Оконный каталог — пример использования, а не обязательная часть любого приложения.

Потребитель описывает свои логические объекты, Events, начальный дистиллируемый граф, исходные подграфы для копирования и композицию библиотечных компонентов. Подключение заголовков и CMake-модулей AppTraverse должно давать один общий механизм запуска, публикации, сохранения и восстановления. Не предполагается копирование из примера сотен строк lifecycle, отдельных sidecar-снимков, native message routing и управления потоками.

Целевые платформы — Windows, macOS, Linux, Android, iOS/iPadOS, Web и **Headless** (тот же объектный граф и модельный runtime без обязательной оконной системы). На них сохраняются смысл объектов, событий, идентичностей, версий, пользовательского состояния и ресурсов. Вид окна, способ запуска процесса, оконный цикл, представление страницы и физический backend хранения принадлежат платформенному слою; Headless исполняет модель и storage без native controls.

Текущий продукт — **локальный функциональный прототип и библиотечный пример**. Сетевая репликация модели, SharedNode, SharedSyncRuntime, ACK-протоколы, presence, Æther network client и соответствующий транспорт не входят в его состав. Название Æther Objects обозначает используемую объектную библиотеку, а не требование подключить сеть. Локальная очередь model/UI и синхронизация потоков не являются сетевой репликацией.

Получение отсутствующих ресурсов — отдельная возможность доставки канонических данных. Оно не синхронизирует пользовательскую модель между устройствами и не требует Æther-транспорта. Плагины, загрузка чужого исполняемого кода, универсальная установка EXE, security-hardening, recovery и полные матрицы аварийных ситуаций не определяют архитектуру этого прототипа.

Полнота архитектуры здесь означает, что её основные понятия совместимы между собой. Она не требует заранее реализовать все возможные источники ресурсов, контролы, схемы миграции или способы компиляции кеша. Неиспользуемая абстракция без работающего потребителя не считается частью готовой библиотеки.

## 2. Система понятий и направление зависимостей

Архитектура состоит из областей ответственности. Каждая область может занимать несколько файлов или targets; таблица не предписывает отдельный manager-класс для каждой строки.

| Область | Ответственность | Не её ответственность |
| --- | --- | --- |
| Объектное основание | Obj, идентичность, Domain, ссылки, регистрация, сериализация слоёв | UI, сеть, прикладные правила |
| Состояние и история | Node, Event, Commit/Apply, base, journal, replay | Создание native controls, выполнение внешних эффектов в Apply |
| Хранилище и поставки | USER, встроенная база, константные состояния, разрешение слоёв | Скрытая закачка при Object Load |
| Runtime модели | Очередь команд, владение model Domain, согласованные публикации | Оконный цикл и прямое управление native UI |
| Runtime представления | UI mirror, обновление графа, привязки и lifecycle presenters | Второй источник пользовательского состояния |
| Компоненты | Переносимые модели контролов, композиция, общие действия | Знание классов конкретного примера |
| Платформенный backend | Native presenters, entry point, event loop, storage binding, packaging | Новая семантика модели и событий |
| Получение состояний | Доставка набора канонических объектов и момент его готовности | Репликация USER и собственный формат объектов |
| Подготовка представлений | Преобразование канонических входов в локальные данные | Хранение единственной копии пользовательской истории |
| Шаблон приложения | Соединение перечисленных механизмов для конкретного потребителя | Фиксированные WindowCatalog root, ID или бизнес-действия |

Объектное основание не зависит от оконных API. Состояние и история используют объектное основание. Модель и headless-воспроизведение не зависят от платформенных presenters. Представление читает публикации модели, а не внутреннее хранилище бизнес-сессии. Получение ресурсов возвращает результат владельцу модели через очередь, но не делает UI-вызовы из рабочего потока.

**Две противоположные линии связи:** пользовательское намерение идёт от native UI к модели; опубликованное состояние идёт от модели к UI. Само намерение не является подтверждённым состоянием, а публикация не является командой повторно применить Event.

**В исходниках.** Существуют `ApplicationModelRuntime`, `ApplicationUiSession`, `ModelObjectProxy`, `WinApplicationHost`, `Presenter`, `Node` и storage-реализации. Общий публичный шаблон приложения как завершённая независимая композиция не следует считать готовым только из-за наличия этих классов. [C01–C06]

## 3. Идентичность объекта и версия состояния

Объект — логическая сущность, не адрес C++-экземпляра. Одно и то же состояние может загрузиться в другой процесс или Domain, не меняя логический ObjId. Переименование файла, перемещение класса между библиотеками и выбор другого native backend также не должны незаметно менять опубликованную идентичность.

| Понятие | Точное значение |
| --- | --- |
| ObjId | Идентичность экземпляра в области данных приложения/Domain; не native handle |
| ClassId | Стабильная идентичность сериализуемого класса или слоя иерархии |
| S | Версия сериализуемого слоя конкретного ClassId |
| Ключ слоя | Сочетание ObjId, ClassId и S |
| Generation | Текущая ревизия материализованного состояния Node для публикации; не S и не R |
| R | Логическая поставка данных и поведения |
| E | Исполняемая сборка для определённой платформы/архитектуры |
| B | Номер встроенной в E исходной поставки |
| Ревизия ресурса | Конкретное каноническое содержимое ресурса/набора состояний |
| Версия рецепта | Способ получения локального производного представления |

Схема и значение различаются. Изменение длины уже сериализуемого вектора — новое состояние того же поля, а не обязательное увеличение S. Добавление нового отдельно читаемого поля/слоя — изменение схемы. Новая логика приложения может потребовать новый E/R, сохранив все S.

Численное значение ObjId не задаёт порядок создания UI, родительские отношения или место объекта в памяти. ClassId не является заменой C++ RTTI во всех произвольных типах: это идентичность зарегистрированного типа объектной системы. Типизация проходит через её ссылки, регистрацию и существующие отношения классов.

Унаследованные части сериализуются своими слоями. У объекта могут одновременно существовать Derived/S0, Derived/S1 и Obj/S1. Совпадение номера S не делает эти слои одним и тем же: их ClassId различаются. Изменение общей системной метаинформации не требует добавлять поле во все прикладные классы.

**В исходниках.** `APPTRAVERSE_NAMED_OBJECT` использует явно заданное serialization-имя для идентичности класса. Поэтому общий `String` может иметь другое C++-имя и расположение заголовка, сохраняя опубликованную identity прежнего строкового типа. Автоматическое изменение идентичности при косметическом rename противоречит контракту. [C07, C15]

## 4. Domain, ссылки и время жизни

`Domain` — локальный контекст экземпляров и их storage. Он разрешает логические идентичности в живые объекты. `DomainGraph` выполняет конкретный обход загрузки или сохранения. Это разные уровни: Domain живёт вместе с сессией, а граф обхода не обязан жить всю сессию.

`ObjPtr` хранит объектную идентичность и семантику загрузки, а при материализации — связь с живым объектом. Валидная ссылка может оставаться незагруженной. Отсутствие cached-объекта не доказывает отсутствия сохранённых данных. Невалидная ссылка, локальные байты незагруженного объекта и ещё не полученный набор ресурсов — три разных состояния.

Несколько ссылок на один ObjId внутри Domain обозначают один логический экземпляр. Загрузка aliases не должна создавать независимые копии одной сущности. При этом model Domain и UI Domain содержат разные C++-объекты даже при одинаковых ObjId: это намеренное разделение владения между потоками, а не нарушение идентичности.

Ссылка на исторический объект может сохраняться в Event или base после удаления его из текущего UI-графа. Поэтому наличие объекта в `Domain::Find` не равно его участию в текущем представлении. Для UI нужна достижимость по актуальным связям, а не по всей истории.

Операции объекта требуют живого Domain и живого storage. Возможность безопасно снять запись из реестра при разрушении объекта не даёт разрешения использовать его после завершения Domain. Долговечная identity не продлевает жизнь C++-контекста. Возвращать указатель из функции с локальным Domain и затем продолжать загрузку/сохранение через него нельзя.

Владеющие ссылки удерживаются на время загрузки связанного графа и смены topology. Сырой адрес из поля базового подобъекта не должен использоваться для восстановления отдельного владельца с неверным layout. Уже полученная каноническая владеющая ссылка из Domain предпочтительнее повторного конструирования владения по базовому адресу.

**В исходниках.** `InitializeRuntimeNode` и `CaptureStructuralPresentationKeepalive` используют `Domain::Find` для получения корректной владеющей ссылки. `DomainRegisteredObjects` введён на уровне зависимого object runtime для регистрации/разрегистрации. Это механизм lifetime, а не дополнительное хранилище происхождения или пользовательского состояния. [C06, C08, C09]

`DomainGraph` содержит состояние текущего обхода, включая обнаружение повторных посещений. Для независимого сохранения после загрузки в действующем коде используется новый экземпляр графа. Переиспользование одного обхода для несвязанных операций не является контрактом приложения. [C10]

## 5. Виды состояния и единственный источник истины

AppTraverse различает данные по смыслу, а не только по месту размещения. Одни и те же байты в памяти не становятся пользовательским состоянием автоматически.

| Вид | Владелец и роль | Можно ли восстановить без потери пользовательских данных? |
| --- | --- | --- |
| Каноническая поставка | Неизменяемые исходные состояния и ресурсы выбранной ревизии | Из соответствующей поставки, если она сохранена/доступна |
| USER | Динамические слои, настройки, исторические снимки и Events | Нет, это самостоятельные данные пользователя |
| Живой model graph | Материализация канонического состояния и USER в сессии | Да, из сохранённого состояния; несохранённые изменения ещё существуют только здесь |
| UI mirror | Согласованная проекция состояния для UI-потока | Да, новой публикацией модели |
| Компилированный кеш | Производные байты конкретного рецепта и устройства | Да, из канонического источника и того же совместимого рецепта |
| Runtime-ресурсы | Окна, View, DOM, GPU-объекты, подписки, mutex, очереди | Пересоздаются средствами runtime |

Константность относится к экземпляру, не к C++-типу. Один String может быть переводом поставки, другой — пользовательским текстом. Один класс окна может иметь исходный шаблон и созданные из него динамические экземпляры. Все aliases одного объекта обязаны видеть одну роль const/dynamic.

Новый набор состояний константы не является пользовательским редактированием старой константы. Он публикуется в контексте определённой поставки или компонента, после чего resolver выбирает активные байты. Event не должен менять supply-константу «на месте» ради применения обновления.

UI mirror не является переносимым пользовательским профилем. Runtime-поле `presentation_loaded` не означает сохранённое намерение пользователя открыть окно. Кеш не хранит единственную копию строки или изображения, нужную для replay. Каждое из этих различий влияет на то, какие ссылки обходятся и какие данные сохраняются.

Отдельно различаются **логическое состояние** и **факт локальной материализации**. Изменение выбранной страницы — пользовательское действие. Создание native View этой страницы — следствие представления. Выбор нового ресурса может быть Event; загрузка уже выбранных неизменных байтов в RAM не обязана создавать новое бизнес-событие.

## 6. Штатная сериализация и области обхода

Единая сериализация строится на `DomainGraph`, объектных ссылках, `Load/Save(Version<S>)` и `BinaryArchive`. Состав данных описывается объектной системой, а не параллельным протоколом полей, длины и offsets, придуманным приложением.

Этот контракт распространяется не только на отдельные окна. Checkpoint, публикации, replay-пакет, метаданные поставки, задачи получения и метаданные кеша также должны иметь штатно сериализуемое описание. Помещение прежнего самописного envelope в `vector<byte>` не делает его семантику штатной сериализацией. Непрозрачный payload изображения или внешний native resource format — другое понятие: это данные ресурса, не скрытый второй serializer графа.

Одна система сериализации может иметь разные **области обхода**. Для постоянного состояния нужны история, локальные связи и происхождение. Для интерфейса нужны актуальные поля и текущая topology. Отказ от сетевой репликации не означает слияние persistent и presentation scopes.

| Область | Состав | Что исключается |
| --- | --- | --- |
| LocalPersistent | Каноническое динамическое состояние, нужные base/journal, origin и локальные persistent-связи | Native handles, callbacks, временные очереди |
| MaterializedPublication | Актуальные значения, материализованные связи и данные для UI mirror | Бизнес-история как исполняемая история UI, сетевые сущности |
| Набор состояний поставки | Точные объектные слои и метаданные их принадлежности | USER и runtime-кеши |
| Replay-пакет | Исходное состояние, Events и закреплённые зависимости | Оконные ресурсы и повторное выполнение внешних операций |

Смысл S задаётся классом. Сохранение известного слоя не удаляет другие слоты только потому, что текущий код их не читает. `ShouldSaveVersion` относится к прикладной политике конкретного класса; системный origin-фильтр не должен неожиданно подавлять Derived/S1 у всех наследников.

**В исходниках.** Поля классов сериализуются штатно, но `ByteSink`/`ByteSource` в `publication_channel.h` и `object_serialization.cpp` вручную упаковывают envelopes публикаций и checkpoint: идентификаторы, длины, поколения и base bindings. Это наблюдаемая реализация, а не исключение из принятого требования к единой сериализации. Семантика этих данных необходима, конкретная ручная упаковка не является архитектурным обязательством. [C06, C11]

## 7. Дистилляция и происхождение начальных значений

Дистилляция — построение начального канонического графа при подготовке приложения/поставки. Она создаёт объекты, задаёт значения, устанавливает ссылки, роли const/dynamic и фиксирует логические identity. Результат — данные, которые приложение загружает, а не повторно вычисляет из набора constructors при каждом старте.

Каноническое поле получает начальное значение здесь. При загрузке значение приходит из сериализуемого слоя. При создании нового экземпляра — из копируемого исходного подграфа. Constructor default не должен скрыто подменять отсутствующее сохранённое значение и создавать другое состояние в зависимости от пути создания.

Это не отменяет runtime-инициализацию. Mutex, thread state, указатели на host, cached native handles и служебные курсоры не приходят из дистиллированных пользовательских данных. Они явно инициализируются соответствующим lifecycle до первого использования. Запрет скрытых defaults не разрешает чтение неинициализированной памяти и не запрещает обычное конструирование STL/RAII-объектов.

Полная встроенная база содержит обязательные стартовые объекты и байты локальных lazy-подграфов. «Не загружено в RAM» не означает «не включено в поставку». Исходники разработки, пути build-host и временные буферы конвертера не являются частью переносимого графа.

Дистилляция Node также подготавливает исходную историю: у логического Node есть согласованный base и пустой журнал. Нормализация начального выпуска допустима на build-time графе. Та же операция над пользовательским графом при shutdown не является обычным сохранением: она может стереть историю, изменить base и сбросить поколения.

Host-exporter работает на машине сборки. При cross-compilation target executable Android/iOS/WASM не используется как запускаемый host-инструмент. Дистиллируемый общий граф не должен требовать native presenter target-платформы для подготовки канонических данных.

**В исходниках.** `FinalizeDistilledGraph` подготавливает Node без base; `InitializeRuntimeNode` создаёт base того же зарегистрированного класса и вызывает `CaptureBaseState`. `StabilizeDistilledPersistentSnapshot` очищает journals, переснимает base и устанавливает generation=1. Последняя функция действительно меняет смысл истории и не равнозначна Save. [C08, C12]

## 8. Хранилище, USER и разрешение слоёв

Storage предоставляет локальные операции над точным ключом слоя: читать, записывать, перечислять классы/доступные данные и обозначать удаление. Внешний путь файла — реализация этого контракта, не часть прикладной identity. RAM, файловый каталог и браузерное хранилище могут реализовывать одну логическую модель без одинаковых путей на диске.

Долговременное состояние приложения сохраняется **только** штатной объектной сериализацией **ObjId / ClassId / S → bytes** через `DomainGraph` и `IDomainStorage`. Физическое размещение (один файл, каталог слоёв, база) — ответственность backend storage, не модели. Отдельный persistent sidecar с поколениями, таблицами base bindings или typed blob-контейнер поверх обычного storage не является целевой архитектурой. Поля `Node::base` и `Node::journal` — сериализуемые слои Node; origin — системный объектный слой.

Для динамического экземпляра его собственный USER-слой имеет приоритет. Если слой отсутствует, встроенный initial-объект получает начальные данные из своей базы, а созданный через Clone экземпляр — из допустимого origin для соответствующего отсутствующего слоя. Простое наложение двух storage с одинаковыми ObjId не решает задачу origin: ObjId экземпляра и исходного prefab различаются.

Supply-константа разрешается только из выбранного канонического источника. Попытка сериализовать достижимую supply-константу при сохранении корня не должна создавать её тело в USER. Пользовательская ссылка на константу при этом законна. Эта политика записи не превращает сам объект в C++ const и не заменяет правило, запрещающее прикладным Events мутировать supply.

Записывается целый слой, а не отдельное поле. При отсутствии USER override можно не создавать файл, если его байты совпадают с базой. Если override уже существует, возврат к базовому значению должен обновить его содержимое: нельзя оставить в USER старые отличающиеся байты и считать запись ненужной. Автоматическое удаление override — самостоятельная политика, не следствие сравнения одного нового буфера.

Удалённый слой и никогда не существовавший слой имеют разный смысл. Иначе пользовательское удаление может незаметно «воскреснуть» из BACKING. Физическое удаление объектов, всё ещё нужных base или журналу, нельзя выводить только из отсутствия живого окна.

`force_materialize` нужен для закрепления исторического снимка даже тогда, когда его значения совпадают с текущей базой. История должна остаться прежней после смены supply. Этот флаг относится к выбору записи слоя; он не означает немедленную загрузку всей модели или универсальную eager-политику ссылок.

**В исходниках.** `OverlayDomainStorage` поддерживает RAM или внешнее writable storage. Для supply IDs `Load`/`Enumerate` обращаются к backing, а `Store` возвращает discard-writer. Уже существующий USER-слой записывается напрямую; сравнение с backing используется только при его отсутствии. `force_materialize` направляет запись в USER. `DirectoryDomainStorage` хранит слои по каталогам identity и имеет save-session/commit-учёт. Сам overlay не выполняет универсальную инициализацию нового S через origin. [C13, C14]

Нормальный штатный Save и атомарность при аварии — разные свойства. В контракте прототипа сохранение должно восстанавливать ожидаемое состояние после обычного завершения, но документ не обещает транзакцию всех файлов при отключении питания.

## 9. Ленивый граф, достижимость и выгрузка

Lazy loading сохраняет логический граф полным, даже когда в памяти присутствует лишь его часть. Ссылка содержит идентичность и политику загрузки; локальный storage содержит тело. Необязательный ресурс, ещё не полученный на устройство, является другим состоянием и не должен скрыто скачиваться при обычном Object Load.

Для разных операций требуется разная достижимость. Один универсальный обход всех полей без понимания scope не подходит одновременно для UI, сохранения истории и Clone.

| Обход | Какие связи важны |
| --- | --- |
| Живое представление | Текущие модельные связи, необходимые отображаемому UI; без объектов, удерживаемых только историей |
| Persistent-состояние | Данные, ссылки и история, необходимые восстановлению сессии |
| Clone | Копируемое замыкание с учётом роли объектов и границы внешних ссылок |
| Набор получения | Отсутствующие состояния выбранного ресурса и его зависимости |
| Replay | Исходное состояние, Events и исторически закреплённые зависимости |

Наличие cached-pointer может ускорять обход, но не определяет его семантику. Незагруженный динамический ребёнок не превращается во внешнюю shared-константу, а Event-held удалённый объект не становится live presenter. Факт «объект есть в Domain» и факт «объект достижим из текущей композиции» нельзя подменять друг другом.

Обычный Save не должен принудительно грузить ленивый граф ради повторной записи уже существующих байтов. Сохранение ссылки и сохранение её тела — разные действия. Полный переносимый снимок может включать байты незагруженных зависимостей, но сам факт упаковки не требует делать их активными в приложении.

**Закрытие, выгрузка и удаление не синонимы.** Закрытие прекращает показ. Выгрузка освобождает материализацию, сохраняя адресуемые данные. Удаление меняет логический граф через Event. Запись каталога может остаться после закрытия окна, а историческая ссылка — после удаления записи из актуального списка.

Наличие локальной копии ресурса также не равно наличию native-представления. Изображение может быть получено, но не декодировано; строка может иметь сериализованные байты, но не быть загружена; presenter может существовать в зеркале, но ещё не пройти активацию после загрузки родителя.

**В исходниках.** Есть отдельные `CollectLiveReachableObjects`, `CollectPersistentSerializationReachableObjects`, `CollectLiveReachableNodes` и другие обходы. `FindLiveReachableNode` существует именно потому, что `Domain::Find` может вернуть объект, удерживаемый историей. Штатное durable-сохранение (`DomainGraph::SaveRoot` / `LoadRoot` через `IDomainStorage`) записывает canonical state, historical `Node::base` и `journal` обычными объектными слоями; отдельный persistent checkpoint больше не требуется для восстановления. [C06]

## 10. Events и изменение модели

После дистилляции, загрузки или создания подготовленного экземпляра постоянное логическое состояние изменяется через Events. Native действие является намерением. Модель превращает его в типизированный переход, фиксирует в журнале и применяет к своему состоянию. UI не пишет значения напрямую по адресу модельного объекта.

`Event` — сериализуемое описание перехода с достаточными входными данными. `Node` — логическая сущность, история которой связывает исходную базу, упорядоченные Events и материализованное состояние. Не каждый объект обязан быть Node: обычная строка или описание представления могут изменяться в рамках события владеющего Node, не создавая собственного бизнес-журнала.

Логическая последовательность: намерение → подготовка Event → Commit → запись в порядок истории → Apply → изменение материала модели → уведомление runtime → публикация. Это последовательность ответственности, не требование сетевого протокола или отдельного класса на каждую стрелку.

Apply детерминирован относительно Event и закреплённых данных. Текущее время, случайный выбор, новые случайные identity, результат внешней операции и сведения устройства должны попасть во входные данные до применения, если они влияют на воспроизводимый результат. Повтор Apply не должен создавать другое окно с другим ObjId или заново обращаться к серверу.

Создание объекта тоже является переходом. Подготовленный новый подграф может существовать до Commit, но его добавление в живой прикладной граф и соответствующие значения описываются Event. При replay используется та же identity и то же исходное состояние, а не новая генерация IDs. Удаление/смена ссылок также меняют topology через Events.

Runtime-факты не обязаны становиться бизнес-историей. Progress закачки, создание HWND, принятие UI публикации, чтение из кеша и изменение локального cached-pointer — не изменение выбранного пользователем содержания. Они могут требовать публикации представления, но не Event на каждое техническое действие.

Производные UI-свойства требуют явного смысла. Например, доступность кнопки Open может выводиться из наличия выбора. Она не должна становиться независимой второй настройкой, которую другой код меняет в обход логического правила. Источником истины остаётся состояние выбора; производная материализация обновляется согласованно с ним.

**В исходниках.** `NodeFor`/`EventFor` обеспечивают типизированную диспетчеризацию. `Node::CommitInto` строит `EventRecord`, выбирает порядок относительно последнего события и вызывает вставку. `NoteMaterializedChange` увеличивает generation и уведомляет runtime. В `WindowCatalog` есть отдельные Events добавления, удаления, выбора и open-state. `AddWindow` пока вручную создаёт holder, window и presenter до `Commit`, а не вызывает универсальный prefab Clone. [C05, C16, C17]

## 11. Исторический base, journal, persistence и replay

Основной инвариант истории: **исторический base плюс упорядоченный журнал воспроизводят текущее логическое состояние**. Сравниваются значения и связи, а не адреса C++-объектов. После загрузки из storage runtime должен знать, какие Events уже учтены в материализованных полях, чтобы следующий Commit не повторял Apply уже применённого хвоста.

`Node::base` — отдельный исторический снимок. Он не является текущим prefab и не обновляется вместе с defaults поставки. Его identity может быть создана в USER и никогда не существовать в исходной дистилляции. Если заменить base актуальными defaults, старый журнал начнёт вычислять другой результат.

Generation отражает текущую материализацию для UI publication и не требует отдельного persistent sidecar. Позиция уже применённого хвоста — служебное состояние replay. Их нельзя путать с номером схемы или с фактом того, что журнал прочитан с диска.

Компактация сворачивает допустимый префикс истории в новый base и оставляет эквивалентное текущее состояние. Она не должна выглядеть как новое пользовательское действие и увеличивать generation только из-за перепаковки истории. Если текущий executable не понимает сохранённые слои или смысл нужного события, непрочитанный хвост не уничтожается.

Полная компактация требует сохранности нового base и связи владельца с ним. Частичная — восстановления соответствующей точки, захвата нового base и replay оставшегося хвоста. Обычный shutdown не является разрешением вызвать `journal.clear()` и переснять базу без этой семантики.

**В исходниках (срез 8c863bc, исторически).** Отдельный `SerializePersistentModelSnapshot` и sidecar `persistent_model_checkpoint.bin` упаковывали слои, поколения и Node→base вне обычного storage; этот путь снят с эксплуатации. Актуальный контракт — штатный `SaveRoot`/`LoadRoot` через `IDomainStorage`: canonical state, historical base и journal сохраняются в сериализованных слоях Node и связанных объектов. [C06]

При корректном восстановлении новые Events продолжают историю. При загрузке только слоя с отсутствующим base `TryInsertEvent` может отказать: это различие путей восстановления, а не повод автоматически придумать новый base из текущих значений.

**В исходниках.** `CompactJournalInto` учитывает известность сохранённых версий объекта и его base, а `CollapsiblePrefixCount` — допустимость каждого Event. Реализация содержит прямые runtime-проверки и исторические sync-поля; их наличие не означает, что сетевая синхронизация относится к принятому локальному контракту. [C05]

## 12. Prefab, Clone и происхождение каждого узла

Prefab — обычный объект, выбранный как источник копируемого подграфа. Отдельный фундаментальный тип Prefab или специализированный указатель на каждое поле не нужен. Источник может быть константным корнем поставки или уже созданным динамическим экземпляром.

Clone копирует **актуальное каноническое состояние**, включая несохранённые изменения в памяти. Копия последнего persisted snapshot является другой операцией. Это различие существенно: пользователь мог изменить экземпляр, а затем создать его копию до Save.

Каждый динамический узел копируемого замыкания получает новый ObjId. Временная таблица old→new строится один раз на операцию. Две ссылки на один исходный узел должны вести на один новый узел; цикл сохраняется, а не раскручивается в бесконечное дерево. Пользовательские поля, случайно содержащие такое же число, не являются объектными ссылками и не могут меняться бинарным поиском байтов.

Внешние const-referents остаются общими. Явное копирование самой константы как выбранного корня создаёт новый dynamic root; вложенные константы по умолчанию не копируются. Классификация идёт по роли конкретного объекта и границе копирования, не по имени класса или одному loaded-флагу. Если несколько дочерних элементов должны быть независимыми динамическими экземплярами, это должно следовать из описания исходного графа, а не из случайной eager-загрузки.

Для каждого клонированного узла сохраняется **соответствующий ему origin**. У дочернего объекта не должен появляться origin корня P только потому, что он входит в тот же Clone. В цепочке P→A→B→C устойчивая исходная identity сохраняется по каждой линии происхождения; нет необходимости держать вечно всю цепочку A и B.

Origin — системная lazy-ссылка. Она не делает экземпляр константой, не является native-адресом и не должна материализовать источник при обычном Save или обходе. Тело P не копируется в USER вместе с этой метаинформацией. Таблица remap остаётся временной структурой операции, а не вторым постоянным origin-registry.

Для загруженных узлов snapshot берёт текущее состояние. Для незагруженных нужны их адресуемые слои и та же семантика принадлежности замыканию. Отсутствие cached-pointer не является основанием оставить ссылку на старый динамический узел. Сохранение lazy означает, что необходимые байты и новые связи можно подготовить без обязательной активации всех объектов и presenters.

**История при Clone.** Копия текущего состояния не обязана наследовать чужой бизнес-журнал. Новый Node должен иметь согласованную собственную исходную базу; иначе replay исходного журнала может повторно применить уже учтённые действия или ссылаться на старые identity. Точное оформление истории многоузлового Clone не подтверждено текущим кодом и не должно выдаваться за реализованную универсальную политику.

**В исходниках.** `Obj::SetOriginId` создаёт unloaded `ObjPtr`; origin хранится отдельным `Obj/S1` и автоматически сохраняется в `LocalPersistent`. `CloneCanonicalRoot` берёт RAM-снимок штатным Save, но допускает только один объект, переносит его слои под новый ID, загружает, устанавливает origin и сохраняет новым `DomainGraph`. Remap графа, все lazy-сценарии и история Node таким кодом не доказаны. [C09, C10]

## 13. Эволюция экземпляра без live inheritance

Clone — снимок, а не постоянное наследование всех будущих defaults. Изменение исходного prefab не вправе молча переписать уже существующие собственные слои экземпляра. Новый экземпляр может получить новые начальные значения, а прежний сохраняет свой смысл и историю.

Минимальная поддерживаемая эволюция аддитивна по слоям. Когда новый executable понимает новый S, экземпляр сначала использует собственный USER-слой. Если именно этот новый слой отсутствует, источник начальных данных определяется origin и совместимой поставкой. Не заменяются старые S0, не сливаются произвольно отдельные поля и не выбирается текущее изменённое состояние случайного динамического предка.

Пример: исходный P имеет S0 с value=150. Экземпляр A изменён Event до 1601. Новая поставка добавляет S1 с tag=252. A получает отсутствующий S1, но его value остаётся 1601. Если пользователь уже сохранил собственный S1, именно он имеет приоритет. Смена defaults поля value в P не означает, что A должен вернуться к новому default.

Historical base эволюционирует отдельно. Он получает только недостающий слой по собственному закреплённому происхождению; старые исторические значения не заменяются текущими значениями владельца. Только тогда replay старых Events остаётся воспроизводимым. Источник новых слоёв base может совпадать по логическому origin с владельцем, но входные исторические данные различаются.

Read-only Load не должен превращаться в скрытую запись миграции. Материализация нового S и создание пользовательского override — разные действия. Повторное обновление не запускает инициализацию заново поверх существующего USER-слоя.

При downgrade старый код читает и изменяет известные ему слои; новые неизвестные слоты остаются доступными следующему новому executable. Смена E/R не откатывает пользовательские действия копированием старого профиля поверх текущего. Также нельзя незаметно изменить семантику старого Apply и назвать это совместимостью только потому, что формат S0 прочитался.

Dynamic-source без устойчивого origin не получает автоматически происхождение от временного ObjId, который может быть удалён. Для описанного прототипа источники имеют явно закреплённое происхождение. Универсальная политика для произвольного динамического источника без него не выводится из API `CloneOptions::stable_origin` и остаётся отдельным ограничением поддерживаемого сценария.

## 14. Model runtime: очередь, изменения и публикация

Model runtime владеет выполнением операций над model Domain. UI и рабочие задачи передают ему намерения, а не получают право конкурентно менять его граф. Это локальная модель владения потоком; наличие общей процессной памяти не делает доступ к объектам произвольно потокобезопасным.

`ModelObjectProxy` адресует логическую цель по ObjId. Аргументы команды переходят границу потока значениями с достаточным временем жизни. На model thread цель разрешается через Domain и вызывается прикладной метод, который формирует Event. Захваченный UI pointer на модельный Node или lambda, ссылающаяся на уже уничтоженный локальный буфер, не соответствует этой границе.

Proxy-команда и Event различаются. Команда — runtime-запрос выполнить прикладное намерение. Event — сохраняемое описание принятого изменения. В текущем локальном runtime вызов метода может передаваться C++ callable; это не wire-формат истории и не основание сериализовать адрес member-function в replay-пакет.

Model runtime связывает живые Node с уведомлением о материализованных изменениях. После Apply или другого разрешённого изменения представимого состояния он знает, что нужна публикация. Исторические base не должны становиться самостоятельными источниками live-уведомлений: они могут заменяться при compaction, а их изменение не равно новому пользовательскому действию.

Канал публикации имеет собственное состояние занятости. Выполнение model work не должно останавливаться только потому, что UI ещё держит предыдущий снимок. Новые изменения могут накопиться, но непрочитанный снимок нельзя перезаписать. Следующая согласованная публикация отражает актуальный результат модели. Это не означает потерю Events: журнал и частота отображаемых кадров — разные линии.

Событие «данные опубликованы» вызывается после завершения записи снимка, а не посередине изменения графа. UI читает стабильные данные, не наблюдая отдельные присваивания модели. Количество публикаций не обязано совпадать с количеством Events, а structural-публикация не обязана быть минимальным бинарным diff.

**В исходниках.** `ApplicationModelRuntime::Run` сначала вызывает `SerializeInitialPublication`, затем обслуживает очередь `ModelWork`. `PendingDirtyNodes` служит сигналом к публикации; runtime вызывает `SerializeStructuralNodePublication(application_root, ...)` для корня, когда канал свободен. Таким образом, название Incremental сейчас не доказывает передачу только изменённых полей. `PublicationChannel<3>` разделяет producer, опубликованный и удерживаемый UI буферы; `TakePublishedCopy` копирует байты и освобождает слот. [C01, C02, C11]

При `RequestStop` новые задания больше не принимаются; уже поставленная работа в текущем runtime дорабатывается, после чего управление возвращается lifecycle приложения для сохранения. Требуется различать завершение model loop и завершение всего приложения: persistence и уничтожение Domain ещё могут происходить после выхода из цикла.

## 15. Зеркало интерфейса: отдельный граф, а не общая память

UI mirror — отдельная материализация текущего представимого состояния. Оно имеет собственный Domain, storage и C++-объекты, доступные UI-потоку. Логические identity сохраняются для сопоставления с моделью, но адреса, владельцы и runtime-ресурсы различаются.

Зеркало решает сразу несколько задач. Оно исключает необходимость блокировать model graph на каждом paint или native callback. Оно позволяет применять публикацию как согласованное изменение структуры. Оно отделяет native lifecycle от загрузки бизнес-модели. Наконец, оно даёт headless-модели возможность работать вообще без платформенного host.

**Зеркало не является вторым автором USER.** Его поля приходят из публикаций. UI может менять собственные runtime-детали представления — например, привязку к native handle, локальный measurement cache или счётчик активации, — но постоянная настройка и логическое значение возвращаются в модель через Proxy/Event.

Одинаковый ObjId в model и mirror позволяет направить действие к исходному объекту. Он не означает, что `ObjPtr` из UI можно передать модели как живую cross-thread ссылку. Между контекстами передаётся identity и значения, а объект разрешается внутри своего Domain.

Зеркало содержит текущую topology, а не все объекты, когда-либо встречавшиеся в истории. После удаления строки списка Event может удерживать старый holder для replay; такой holder не должен автоматически вернуться в UI. После закрытия окна модельная запись может сохраниться, но native presenter перестаёт быть активным. Исторический base не является дополнительным окном, которое надо показать.

Начальная публикация достаточна, чтобы создать зеркало из пустого UI storage без обращения к живому model Domain. Это не требует включать в неё весь ленивый graph: нужны данные текущего представимого подграфа и корректные ссылки. Когда позже материализуется новый участок, structural-публикация переносит его состояния и связь с существующим UI-корнем.

В UI не выполняется replay журнала ради каждого кадра. Оно принимает уже вычисленные значения и поколения. History omission является существенным контрактом: иначе стоимость представления росла бы вместе со всей историей и возникало бы второе исполнение бизнес-событий.

**В исходниках.** `ApplicationUiSession` содержит отдельные `RamDomainStorage` и `Domain`, загружает `LoadInitialPublication`, затем активирует presenters. `FinalizeUiNodeState` принимает опубликованное поколение и очищает `base`/`journal` у UI Node. Это не удаление пользовательской истории: очищается отдельная UI-копия. Деструктор сессии вызывает `UnloadPresenters`. [C03, C06]

Ключевое следствие: сериализация persistent-модели и публикация зеркала могут использовать одни классы и штатные механизмы, но разные scopes. Один класс не означает одинаковое содержимое всех его материализаций.

## 16. Применение публикации и изменение topology

Field-update меняет значения уже существующих объектов. Structural-update может добавить объект, заменить связь, активировать ленивую часть, убрать текущую достижимость или изменить набор presenters. Одинаковая функция «пересоздать всё» скрыла бы эти различия и приводила бы к потере native-состояния, фокуса и лишним подпискам.

Во время structural-apply переживающие обновление объекты должны сохранить корректное время жизни. Изменение root-ссылок может временно снять последних владельцев, а удаляемому presenter ещё необходимо выполнить native `OnUnload`. Поэтому ссылки для удержания объектов относятся к нормальному lifecycle, а не к защитному «пусть хоть как-то работает».

Правильная граница применения выглядит так: имеющееся зеркало удерживается; новые состояния становятся доступны его storage; объекты и ссылки согласованно обновляются; определяется новый live-граф; прекращается представление удалённых узлов; активируются новые; сохранившиеся presenters получают уведомление о новых значениях. Native-код не должен получать промежуточную topology, где родитель уже исчез, а ребёнок ещё используется.

Порядок сериализации файлов, численный ObjId и порядок native-показов — независимы. Родительский native ресурс нужен до активации ребёнка; при освобождении порядок обратный. Существующие объекты могут обновляться на месте, чтобы их runtime-привязки не исчезали при каждом поступлении новых данных.

Повторная публикация не создаёт второй экземпляр подписок и второе окно той же активной сущности. `OnModelChanged` — обновление существующего представления, не повторный `OnLoad`. Снятие связи из live-графа не уничтожает канонические данные, ещё нужные истории или каталогу.

Если UI-снимок использует generation или границу изменений, эти данные не смешиваются с номером S. Отображение новой ревизии одной схемы не требует регистрации нового класса. Полная согласованная публикация может быть проще diff-протокола и полностью достаточна для прототипа.

**В исходниках.** `CaptureStructuralPresentationKeepalive` удерживает живые объекты и активные presenters. `ApplyStructuralPublicationAndUpdatePresenters` применяет envelope, затем обновляет native lifecycle. `UpdatePresentersAfterStructuralPublication` вычисляет удалённых presenters, выгружает их в обратном порядке и инициализирует новых. `DeserializeObjectGraphFromBuffer` inject-ит слои в UI storage и отдельно обновляет объекты свежими обходами. [C06]

В loader текущего среза также есть повторные проходы hydration и диагностические fallback-пути. Они не являются архитектурным требованием к формату публикации. Требование — полностью согласованное зеркало и корректный lifecycle, а не сохранение конкретного числа повторных Load.

## 17. Presenter и native lifecycle

Presenter связывает переносимое описание контрола и данные UI mirror с представлением. Он не обязан быть Node и вести собственный бизнес-журнал. Конкретный backend отвечает за native resources; общая часть — за смысл привязок и связь с моделью.

Три уровня должны быть различимы: модель контрола; нейтральное описание/логика presenter; native реализация. Приложение выбирает композицию и действие. Библиотека обеспечивает native message routing, model proxy, локализацию и повторно используемый lifecycle. Платформенный presenter не должен решать, как WindowCatalog нумерует новые окна или какой Event означает Delete.

| Фаза | Данные и действия |
| --- | --- |
| Object Load | Сериализуемые поля и связи восстановлены; native окно ещё не создаётся |
| Привязка | Presenter связан со своим mirror, host и proxy; известны зависимости |
| Активация | На UI-потоке создаются native ресурсы, родитель раньше ребёнка |
| Обновление | Новая публикация отражается в уже существующем native объекте |
| Деактивация | Снимаются подписки и ресурсы, дети раньше родителей |
| Уничтожение объекта | Освобождается объектная материализация после завершённого lifecycle |

Object Load не должен создавать HWND, JNI View или DOM-узел. Иначе обычное чтение состояния из headless-теста внезапно стало бы оконной операцией, а загрузка base для replay — показом исторического интерфейса. По той же причине обычный деструктор объекта не заменяет явное закрытие native-представления на правильном потоке.

Native handles, адреса callbacks, ссылки на host и статус `presentation_loaded` не являются каноническими данными. Переносимыми могут быть описание layout, роль элемента, привязка к состоянию и intent геометрии. Платформенная реализация не должна менять опубликованный ClassId переносимого класса только из-за выбора ОС.

Зависимость от родителя — реальная часть алгоритма. Последовательность «сначала parent, затем child» не равна retry после неудачного создания окна. В контракте прототипа нет каскада обходов, которые продолжают работу с отсутствующим обязательным native ресурсом. Если рабочий путь требует parent, это устанавливается при композиции и activation.

**В исходниках.** Базовый `Presenter` — `ae::Obj`, не Node. Он имеет `OnLoad`, `OnModelChanged`, `OnUnload`, `ReadyForPresentation` и runtime-ссылки на host/proxy. `InitializeNewPresenters` использует multi-pass по готовности и ведёт `presentation_load_order`; выгрузка идёт в обратном порядке. Обязательные связи дистиллированного графа не дублируются optional-проверками и fallback в runtime (P2.X1). [C04, C06]

## 18. Шаблон приложения и владение сессией

Библиотечный template — готовая композиция механизмов, а не одна обязательная C++ template-метафункция и не копия файла `main`. Его смысл в том, что независимый потребитель получает стандартный lifecycle, задавая только собственное содержимое и несколько точек интеграции.

Приложение владеет определением root-модели, своих Node/Event, дистилляцией, prefab-графами, ресурсными зависимостями и UI-композицией. Библиотека владеет общим способом загрузить эти данные, восстановить историю, запустить model runtime, опубликовать зеркало, подключить backend и штатно завершить сессию.

| Потребитель предоставляет | Библиотека предоставляет |
| --- | --- |
| Root type и его логическую identity | Domain/storage-композицию и загрузку |
| Регистрацию собственных классов | Единый механизм регистрации и применение слоёв |
| Начальный граф и prefab | Build-time distillation/export и загрузку встроенной базы |
| Прикладные Events и композицию | Очередь model work, публикацию и UI mirror |
| Выбор поддерживаемого backend | Native lifecycle и переиспользуемую оболочку |
| Политику нормального завершения приложения | Остановку runtime, сохранение и освобождение ресурсов |

Нормальный startup: подключить код и регистрации; определить встроенный supply и USER; загрузить модель и её историю; подготовить текущий представимый подграф; опубликовать initial state; построить mirror; активировать presenters. Это цепочка обязанностей, не разрешение повторять её вручную в каждом приложении.

Нормальный shutdown: прекратить приём новых намерений; завершить уже принятую model work; сохранить требуемое состояние; завершить model session; присоединить её поток; снять native представления UI и освободить mirror. Конкретный порядок освобождения model и UI должен исключать callbacks в уже завершённую модель; UI не владеет её raw pointers.

Мобильное сохранение связывается с реальным lifecycle оболочки, а не только с desktop-событием закрытия главного окна. В Web есть завершение/приостановка сессии и persistence backend браузера. Общий контракт сохраняемого состояния остаётся тем же, хотя точка его вызова отличается.

CMake-подключение не должно предполагать, что AppTraverse является корневым проектом. Пути библиотеки разрешаются относительно её модулей; потребитель может иметь собственный `CMAKE_SOURCE_DIR`. Система генерации и упаковки поддерживает host-exporter и отдельный target-runtime.

**В исходниках.** `WinApplicationHost` соединяет runtime, proxy, loading/message host и `ApplicationUiSession`. `Run` запускает model callback, обслуживает цикл и выполняет `JoinModelThread` до уничтожения UI session. WindowCatalog и MinimalApp загружают и сохраняют модель через штатный `DirectoryDomainStorage` и `DomainGraph` (без отдельного checkpoint sidecar). Переиспользование runtime существует, но весь lifecycle ещё не является одной готовой библиотечной точкой входа. [C03, C18, C19]

**В исходниках (дополнение, U5.1, тот же SHA).** При штатном shutdown WindowCatalog и MinimalApp вызывают `DirectoryDomainStorage::BeginSaveSession()` до сохранения окон и объектов, проверяют `SaveSessionHadFailure()`; при ошибке пишут в stderr через `WriteFatalStderr` и возвращают код `1` из lifecycle, который `main` передаёт как exit code процесса после `JoinModelThread`. Это явная передача ошибки вызывающему коду, а не атомарность профиля и не production-hardening.

## 19. Общие компоненты и смысл WindowCatalog

UI-компонент включает переносимое состояние, описание представления и связь с прикладным действием. Наличие библиотечного PushButton означает, что потребитель не повторяет native command routing, enabled-state отображение, чтение локализованного текста и отправку model intent.

Прикладная специализация задаёт действие, а не становится второй реализацией контрола. Например, Add вызывает модельное действие создания; Open — выбора/открытия логического объекта. Общая кнопка не знает ни `WindowCatalog`, ни номер строки каталога. Native presenter также не содержит соответствующего бизнес-правила.

Композиция хранится как объектный граф: контейнер имеет элементы, окно связано с presenter, presenter — с источником данных, строковыми/ресурсными связями и родительским представлением. Одна каноническая связь не дублируется в нескольких местах ради удобства платформенного кода. Выражение «UiPushButton → presenter → localization» определяет разделение ответственности, а не обязательную миграцию существующего S0 при переносе одного поля.

WindowCatalog демонстрирует каталог логических визуальных областей. Holder живёт в списке независимо от наличия активного native окна. У окна есть identity, состояние, описание представления и пользовательские параметры. Выбранная строка списка — модельное состояние; фокус native окна может быть runtime-командой представления, не второй копией выбора.

Add создаёт самостоятельный dynamic экземпляр исходного подграфа и добавляет запись Event. Open материализует нужную часть и активирует отображение. Close снимает представление и при необходимости выгружает тело, сохраняя запись. Delete меняет topology каталога; историческая достижимость учитывается отдельно.

Геометрия тоже имеет несколько смыслов. Размер содержимого задаёт доступную область layout. Положение внешней desktop-рамки, Z-order и текущая мобильная страница зависят от оболочки. Общая модель не обязана создавать фиктивные координаты рабочего стола на телефоне. Если параметры намеренно сохраняются, native изменение сообщает их в модель Event, а обновлённое состояние возвращается через mirror.

**В исходниках.** Есть `UiPushButton`, `UiPushButtonPresenter`, `UiListContainer`, `UiPresentedWindow`, `UiDesktopWindow`, оконные presenters и locale-объекты. `WindowCatalog::AddWindow` пока выбирает `WinDesktopWindowPresenter` через платформенную ветку и вручную задаёт исходные поля. `window_catalog_graph.cpp` содержит прикладные кнопки рядом с Win32-композицией. Работоспособность демо не доказывает полной независимости его canonical graph от Windows. [C15–C17]

MinimalApp служит независимым минимальным потребителем. Его архитектурная ценность — возможность собрать другое приложение со своим root без файлов WindowCatalog. Он не должен становиться вторым местом хранения framework-кода.

## 20. Контракт семи платформ

Общими являются модель, Events, canonical identity, origin, слои S, история, ресурсные связи и смысл пользовательских действий. Платформа предоставляет способ отобразить их и связать с системой. «Только presenter платформозависим» означает отсутствие native-логики в модели и компонентах; entry point, event loop, backend хранения и упаковка также объективно остаются платформенными, но принадлежат переиспользуемому адаптеру.

| Платформа | Существующая опора в репозитории | Смысл библиотечного backend |
| --- | --- | --- |
| Windows | `src/platform/windows`, `WinApplicationHost`, Win presenters, WindowCatalog | Native окна и controls; сообщения поступают в общую модель через proxy |
| Linux | `examples/surfaces_demo/linux`, GTK3 presenters и host | Та же композиция и события через GTK, без Win32-объектов в общем графе |
| macOS | `examples/surfaces_demo/macos`, AppKit/ObjC++ и SwiftUI content | Главное UI-окружение и native представления при общей C++-модели |
| iOS/iPadOS | `examples/surfaces_demo/ios`, UIKit/SwiftUI и mobile presenter | Страницы/области той же модели и платформенный lifecycle |
| Android | `examples/surfaces_demo/android/native`, JNI и native runtime | Мост native оболочки к общей модели; представления не сериализуют JNI handles |
| Web | `examples/surfaces_demo/web`, DOM bridge, Emscripten и IDBFS | Браузерный UI, отдельная модельная работа и локальное состояние браузера |
| Headless | `tests/application_contract_headless_test.cpp`, `tests/application_model_runtime_test.cpp`, `tests/model_persistence_test.cpp` | Тот же DomainGraph и storage; модель, Commit и replay без HWND/GTK/JNI/DOM |

Таблица описывает имеющиеся исходные опоры, не доказанную готовность одного WindowCatalog на всех системах (включая Headless E2E). Порт старого Surface-примера может содержать полезную native реализацию, но его product-specific граф, команды и lifecycle не становятся автоматически библиотечным template.

Desktop-окно, мобильная страница и браузерная панель могут представлять один логический объект. Сохранение identity и поведения важнее попытки буквально воспроизвести Win32 multi-window на телефоне. При этом общая композиция контролов не должна разветвляться на шесть разных бизнес-моделей.

Данные, подготовленные на одной платформе, не требуют регистраций native-классов этой платформы при чтении на другой. Локальная реализация выбирается после загрузки переносимого описания. Нативные ClassId могут существовать в локальном представлении, но не быть обязательным foreign-слоем общего application state.

Платформенные различия хранения не разрешают сериализовать случайные пути и process handles как постоянные межплатформенные значения. Путь к профилю разрешает backend; ключи объектов и принадлежность USER остаются общими. Аналогично преобразование текста или изображения — локальная подготовка, не смена canonical schema.

Сборочная политика относится ко всем C++/ObjC++ translation units, которые обмениваются объектами. Нельзя подменить целевой запрет RTTI/exceptions локальными flags одного порта или смешивать несовместимые layout Debug/Release. Native-language bridges имеют собственную ABI-границу; они не превращают C++ объекты в общий mutable граф двух runtime.

**В исходниках.** Общая compile policy отключает C++ RTTI и exceptions, но Web CMake старого примера содержит явные `-fexceptions`. iOS CMake ориентирован на simulator-конфигурацию; Android использует Gradle externalNativeBuild как вход. Эти факты ограничивают то, что можно заявлять о переносимости текущего дерева, без вывода о фактически выполненных запусках. [C20–C22]

## 21. Ресурсные состояния и доставка: локализация как пример

Ресурс — обычное каноническое состояние с identity, ревизией и зависимостями. Доставка делает доступными его байты. Materialization создаёт объект. Подготовка representation создаёт локальный результат. Это разные операции; обычный `Object Load` остаётся локальным.

Менеджер получения работает с набором состояний, который ещё не активен в живом графе. После получения всех необходимых объектов набор становится доступен resolver, а выбранное представление переключается согласованной операцией на потоке модели и одной UI publication. Получение байтов всех зависимостей не означает eager-активацию всех объектов в RAM. Это граница успешного алгоритма, не требование транзакций, подписей или crash recovery.

**Локализация — конкретный пример этого же механизма.** У объекта L есть вектор обычных `ObjPtr<String>`. Новое состояние того же L добавляет ссылку: `[EN] → [EN, RU]`. Вместе с ним приходит состояние новой строки RU. Для нескольких подписей передаётся полный необходимый набор изменённых L и новых строк. До его готовности активны прежние состояния и язык. Расширение вектора меняет данные, а не автоматически S. Не нужны второй StringId-registry, специальный ResourcePtr или отдельный формат переводов.

Пользовательский выбор языка — persistent-намерение, меняемое Event. Отображаемый язык определяется готовым набором. Получение не меняет USER-константы и не пишет событие на каждый чанк. Появление локальных байтов также не обязано увеличивать R: если этот точный optional-набор уже относится к выбранной поставке, скачивание лишь делает его доступным.

Строковый объект называется `String` и не зависит от UI. Каноническая кодировка — UTF-8. Для рассматриваемого кода достаточно существующего `std::string utf8`; массив байт не нужен как предпосылка кеша. Native преобразование выполняется только в presenter/backend, а не в модели, Event или общей локализации. Переименование C++-типа не меняет опубликованный ClassId/S0. Постоянный wchar/UTF-16-кеш строк не входит в реализованный путь.

Смена источника backing не обновляет автоматически уже cached-объект с тем же ObjId. Активация нового набора должна согласованно обновить нужные материализации и зеркало; нельзя опубликовать новый вектор со ссылками раньше готовности тел строк. Подробный механизм активации не подтверждён текущим кодом и не подменяется одной сменой указателя storage.

**В исходниках.** Тип ещё называется `ui::UiString`; `UiLocalizationString` хранит вектор строк, а `MaterializeLanguage` выполняет локальные Load/Reset. Windows presenter делает `Utf8ToWide`. Это локальная lazy-локализация, не завершённая доставка нового набора состояний. [C15, C23]

## 22. Компилированный кеш и производные представления

Компиляция канонического состояния в кеш — преобразование данных в локальный оптимизированный формат. Примеры: подготовленное изображение для устройства, индекс канонической таблицы, обработанные данные шрифта. Это не обязательная JIT-компиляция исполняемого кода и не снимок C++-объектов со всеми адресами.

Цепочка ответственности: исходники разработки → дистилляция → канонические состояния → локальное преобразование → производные байты → runtime-ресурс. USER и история идут по другой цепочке: Event → materialized state → base/journal и сохранённые слои. UI mirror также не является постоянным compiled cache.

| Состав ключа кеша | Почему нужен |
| --- | --- |
| Точная identity/revision канонического источника | Один ObjId может иметь разные состояния |
| Зависимые входы | Изменение шрифта или таблицы может изменить результат без смены основного объекта |
| Рецепт и его версия | Другой алгоритм может выдавать иной выход из тех же данных |
| Параметры преобразования | Результат зависит от реально выбранной конфигурации |
| Выходной профиль | Формат, устройство и значимые возможности определяют пригодность результата |

Смена R сама по себе не требует уничтожить весь кеш, если входы и рецепт не изменились. И наоборот, один и тот же R не гарантирует одинакового результата при другом выходном профиле. Hash может идентифицировать содержимое, но это не обязывает прототип строить security-инфраструктуру вокруг каждой записи.

Кеш удаляем, если доступны исходные канонические данные и совместимый преобразователь. Его удаление не удаляет выбранный ресурс, пользовательский язык, журнал или настройки. Недоступность исходного пакета нельзя скрывать утверждением «всё можно восстановить из кеша»: кеш не является единственным архивом состояния.

Дешёвое либо несериализуемое представление может жить только в runtime. Не требуется сохранять результат каждого преобразования на диск. Native handles, callbacks, JNI/Objective-C ссылки и GPU object identity пересоздаются при activation и не должны переживать процесс как валидные значения.

Сериализуемая конфигурация рецепта и метаданные кеша используют объектную систему. Если выход — собственный AppTraverse data object, он тоже использует штатные слои. Непрозрачный результат внешнего кодека допустим как payload, но не как прикрытие самописного формата модели.

Для Windows текстовое представление может иметь UTF-16-форму вместо канонического UTF-8; такой результат принадлежит presentation/backend. Он не требует менять `String`, вводить поле «текущая кодировка» в модель или включать WCHAR в общий формат. В данном прототипе постоянный строковый кеш является описанным контрактом, не реализованной возможностью.

Подготовка ресурса не блокирует model Apply скрытой долгой операцией. Рабочая задача возвращает готовые данные владельцу, после чего их использует presentation. Это не требует заранее создавать универсальную систему фоновых задач, quota-manager или набор пустых cache-интерфейсов.

Сжатие канонических данных и compiled cache тоже различаются. Если применён LZMA, отдельные слои/ресурсы должны оставаться адресуемыми: чтение одной строки не требует распаковки всего графа. Кодек изменяет физическое представление, а не смысл S. Конкретная реализация индексированного сжатия в рассматриваемом срезе не объявляется готовой.

## 23. Поставки, обновления и откаты

Поставка объединяет данные и поведение, но не поглощает USER. R, E, B и S независимы. Константное изменение может дать новый R без новой схемы класса; изменение logic требует подходящего E; новый dynamic S требует кода его чтения/записи и определённого источника начальных значений.

Встроенная B обеспечивает автономный запуск обязательного графа. Дополнительные константные состояния разрешаются относительно явно выбранного R. Наличие файла нового пакета не активирует его, а максимальный номер каталога не заменяет выбор поставки.

Для совместимой цепочки используются применимые дельты выбранного R над базой B. Пакет не должен перекрывать более новую встроенную базу лишь потому, что лежит рядом. Цепочка определяется описанием выпуска, а не обязательным наличием каждого целого номера. Logic-only выпуск может не иметь фиктивной дельты данных.

Дельта хранит целиком изменённые константные слои относительно предыдущего эффективного состояния. Пример A→B→A требует последней записи A, иначе B останется активным. Дельта не содержит USER, business journal и локальный compiled cache. Изменение состава optional-набора также должно иметь определённую ревизию, а не тайную замену старых опубликованных байтов.

Изменение R и обновление уже материализованного графа — отдельные стороны активации. Для логики и схем простой поддерживаемый режим — согласованный переход между сессиями с подходящим executable. Resource-набор известной схемы может стать активным в текущей сессии на границе публикации. Не обещается произвольная hot-миграция всех C++ объектов.

Downgrade выбирает подходящий код и supply, но сохраняет один USER. Старые приложения изменяют известные поля, оставляя неизвестные слои. Возврат к новому E снова видит их. Откат не должен повторять уже принятые Events или подменять historical base текущими defaults. Если B нового E уже содержит более поздние константы, он не обязан уметь изображать любой старый R без соответствующей старой сборки.

Минимальный смысл поддержки версий — не «все комбинации совместимы», а заранее определённые переходы, в которых identity, USER-приоритет, history и источники новых S сохраняют контракт. Manifest в этом смысле — обычные сериализуемые метаданные состава и выбранных ревизий; подписи, preflight всех несовместимостей и recovery не являются обязательной инфраструктурой прототипа.

**В исходниках.** Есть embedded graph/export, supply packages и headless prefab fixtures с выбором выпусков и версиями. Реальные WindowCatalog/MinimalApp всё ещё используют directory bootstrap и checkpoint, а не полную target-цепочку embedded B + active supply + USER. Наличие fixtures не означает универсальную систему обновления работающих приложений. [C19, C24]

## 24. Headless-потребитель и пакет воспроизведения

Headless — режим использования того же model core, а не особая копия бизнес-логики. Он создаёт Domain, загружает каноническое/пользовательское состояние, выполняет Events и получает значения без создания native windows. Presenter не должен быть обязательным условием вычисления логической модели.

Для воспроизведения важны исходный checkpoint или base, упорядоченный журнал, идентичности создаваемых объектов и точные данные, от которых зависели переходы. Build ID/совместимый код и используемые S задают смысл интерпретации. Одного текстового списка «пользователь нажал Add» недостаточно, если повтор должен получить те же ObjId и связи.

Дамп журнала — функциональная операция сохранения объекта данных. Он не требует логгера, трассировщика или телеметрии. Его формат описывается штатной объектной системой; произвольные текстовые сообщения не становятся источником replay.

Replay не исполняет внешние эффекты повторно. Если Event содержал принятый результат получения данных, воспроизводится этот результат с локальными зависимостями. Если событие лишь отражало выбор языка, воспроизводится выбор, а не скрытая сеть. Runtime-прогресс закачки и cache hit не должны менять результат бизнес-истории.

Headless-представление может вообще не создавать presenters, либо использовать реально необходимую нейтральную реализацию для проверки общей presentation-композиции. Оно не подменяет неподдержанный native backend пустым классом, выдающим фиктивный успех.

Архитектурно полезны два разных сценария. Первый восстанавливает состояние из сохранённых слоёв и продолжает новые Events. Второй восстанавливает base и проигрывает journal, получая эквивалентный граф. Их нельзя считать одним и тем же только потому, что оба процесса завершились с кодом 0.

Для функционального примера достаточно конкретного воспроизводимого сценария. Полная матрица повреждений, разных компиляторов, аварий в каждой точке и всех версий — не содержание этого контракта. Отсутствие такой матрицы не разрешает нарушать детерминизм Apply или скрывать, что конкретный replay ещё не реализован.

## 25. Правила реализации и технические ограничения

AppTraverse использует C++20 без compiler RTTI и exceptions. `dynamic_cast`, `typeid`, throwing-ветви и включение exceptions в отдельном target ради обхода архитектурной проблемы не соответствуют контракту. Идентичность объектных классов, typed links, штатная registry и virtual dispatch обеспечивают нужную диспетчеризацию.

В собственных классах не используются in-class initializers. Начальные канонические значения принадлежат дистилляции, а не constructor fallback. Runtime-only ресурсы явно инициализируются до использования в constructor/lifecycle соответствующей сессии. Структурная привязка к базовому подобъекту и обычное конструирование контейнера не должны трактоваться как альтернативная бизнес-инициализация.

Состояние после корректной загрузки не обрастает цепочками `if (!window)`, `if (!presenter)` и `if (!domain)`, предназначенными продолжить работу после нарушения обязательного графа. Обязательное окно не заменяется заглушкой, отсутствующее значение — случайным default, а неудачная операция — silent no-op. При этом отсутствие выбора, закрытое окно, unloaded объект, незавершённый ресурс и свободный слот публикации являются реальными вариантами нормального алгоритма.

Не создаются logger, профилировщик, универсальная telemetry-библиотека, test-only поля production-классов и фиктивные интерфейсы «на будущее». Данные replay остаются обычной функциональностью состояния. Исторически присутствующие diagnostics/counters в исходниках не превращаются в обязательную часть публичного API.

Режим работы с прототипом — Debug и инкрементальные сборки затронутых targets с необходимыми зависимостями. Это не обещание, что изменённый header никогда не потребует пересборки зависимых translation units. Запрещены полный rebuild/clean ради «на всякий случай», удаление build/cache и повторная загрузка всех зависимостей. MinSizeRel запускается только по отдельному запросу. Имеющиеся Release-результаты не выдаются за новые Debug-прогоны.

Завершённые изменения публикуются в рабочей ветке. Принудительная отправка ограничена `integration/unified-application` и защищается точным ожидаемым remote SHA через force-with-lease. Это правило разработки, не архитектурная зависимость runtime. Оно не разрешает терять чужое продвижение, менять main или переписывать исторические ветки произвольно.

В пределах конкретного задания исполнитель не ждёт повторных подтверждений и не создаёт новых архитектурных задач под видом уточнения. Неизвестное поведение отмечается как неизвестное; частично работающий механизм не объявляется завершённым. Документ не навязывает план работ: он задаёт смысл допустимого результата.

## 27. Опорные сценарии для понимания системы

### 27.1 Нажатие кнопки

Native control сообщает действие своему presenter. Presenter отправляет intent через `ModelObjectProxy`, содержащий identity цели и значения аргументов. Model runtime исполняет прикладной метод в своём Domain; тот создаёт Event. Commit/Apply меняет модель и generation. Runtime публикует согласованное текущее состояние. UI session применяет его к собственному графу и вызывает обновление native presenter. В этой цепочке нет прямой записи из native callback в model field и нет повторного Apply в UI.

### 27.2 Создание и закрытие окна

Команда Add получает dynamic-копию исходного подграфа с новыми identity и node-specific origin. Event добавляет её в каталог. Publication переносит новую topology; UI материализует mirror-объекты и активирует native представление. Close меняет логическое open-state и снимает representation, но holder и его persistent-данные остаются. Open снова использует ту же identity. Delete удаляет связь в живом каталоге; история может удерживать объект отдельно.

### 27.3 Сохранение и повторный запуск

Lifecycle заканчивает принятую model work. Сохраняются динамические слои, нужные historical base и journal; supply не попадает в USER. Новый процесс загружает каноническую базу и USER, восстанавливает историю и её признак материализации. Initial publication строит свежее зеркало. Native handles создаются заново. Состояние не зависит от адресов прошлого процесса или наличия compiled cache.

### 27.4 Получение ресурса и смена представления

Модель содержит выбранную логическую цель. Получение готовит недостающий набор состояний вне активного graph. По завершении владельцу модели передаётся готовность всего набора. Новые состояния становятся локально разрешимыми, активируется соответствующая редакция ресурса, и публикация обновляет зеркало. Native presenter преобразует канонические данные в свой формат. При этом Object Load не выполняет сеть, а USER-настройка не превращается в supply-объект.

### 27.5 Новый слой и воспроизведение истории

A уже имеет собственный S0 и origin=P. Новый код понимает S1, которого у A ещё нет. Resolver получает начальный S1 по соответствующему origin, не меняя S0. Historical base достраивается независимо от текущего A. После нового Event собственный S1 сохраняется в USER. Открытие тем же новым кодом через Load или через base+journal должно давать эквивалентное состояние. Возврат к старому коду не уничтожает новый слой.

Эти сценарии описывают смысл системы, а не список обязательных проверок перед каждым изменением. Они позволяют отличить реальное использование архитектуры от ручного обхода, который визуально даёт похожий результат.

## 28. Термины, которые нельзя смешивать

| Термин | Значение в этом документе |
| --- | --- |
| Канонический граф | Переносимые логические данные и связи, независимые от runtime-адресов и native handles |
| Materialized model | Текущее вычисленное состояние модели в памяти; может включать несохранённые изменения |
| Supply | Неизменяемые данные определённой поставки, включая начальные состояния и константы |
| USER | Динамические данные пользователя и история, отдельные от supply и кеша |
| Prefab | Выбранный источник подграфа для Clone; не специальный тип каждого указателя |
| Origin | Стабильная ссылка на источник начальных слоёв конкретного экземпляра |
| Clone closure | Объекты, которые действительно копируются; определяется связями и ролью, не только cached-полями |
| Remap | Временное соответствие исходных и новых identity внутри Clone |
| Historical base | Исходное состояние конкретной истории, не текущие defaults prefab |
| Journal | Упорядоченные принятые Events и их объектные зависимости |
| Checkpoint | Состояние и метаданные, достаточные для согласованного восстановления модели и истории |
| Publication | Согласованное текущее представление для другого локального контекста, не бизнес-команда |
| UI mirror | Отдельный граф UI-потока, полученный публикацией модели |
| Presenter | Связь данных mirror с представлением; не обязательно Node |
| Native backend | Платформенные presenters и системная оболочка библиотеки |
| Distillation | Подготовка исходного графа и начальных данных выпуска |
| Local Load | Материализация уже доступных канонических/USER-байтов |
| Получение состояний | Доставка ещё отсутствующих локально байтов определённого набора |
| Активация | Выбор согласованного набора для реального использования, не сам факт скачивания |
| Compiled cache | Удаляемые локальные данные, производные от источника и recipe |
| Runtime resource | Ресурс текущего процесса/сессии; не переносимая identity |
| Application template | Библиотечная композиция lifecycle и backend, используемая независимыми приложениями |
| Headless replay | Воспроизведение логической истории без native UI и повторных внешних эффектов |
