# UpdateLab

UpdateLab — автономный пример AppTraverse для Windows x64 и Linux x64. Одно нативное окно показывает перевод, список языков, доступные версии, пользовательскую заметку, клоны префаба и прогресс загрузки. За доставку состояния, переводов и исполняемого файла отвечает отдельный клиент Æther.

## Запуск

На Windows из корня репозитория, Visual Studio 2022/v143, Debug.

```powershell
./tools/build_update_lab.ps1
./tools/start_update_lab.ps1 -InitialRelease 1
```

Первый запуск ставит выбранную поставку из полного образа. Следующие запуски используют активный слот той же установки. Скрипт поднимает сервисный клиент и передаёт приложению его UID. Для файлового теста укажите `-FileSource`. Параметры `-Profile` и `-Installation` позволяют создать отдельное устройство. `-StoreDirectory` выбирает каталог поставок.

Для общей поставки сначала соберите Linux-бинарники в WSL, затем передайте их Windows-упаковщику.

```sh
bash tools/build_update_lab_linux.sh /home/nickc/update-lab-build
```

```powershell
./tools/build_update_lab.ps1 -LinuxBinaries '\\wsl.localhost\Ubuntu\home\nickc\update-lab-build\update-lab-package'
```

Один клиент обслуживает обе платформы. Windows-скрипт пишет в `artifacts/update-lab/device-releases`, Linux-скрипт — в `artifacts/update-lab/device-releases-linux`. У Windows-скрипта есть параметры `-Store` и `-Through`, у Linux-скрипта путь переопределяет переменная `UPDATE_LAB_STORE`. Имена компонентов привязаны к версиям. Для пересобранного прототипа с другим содержимым под теми же номерами укажите новый каталог.

Пример установки сразу на R3 с последующей работой через Æther.

```sh
update_lab_provider --store /srv/update-lab --profile /var/tmp/component-client --endpoint-file /var/tmp/endpoint
/srv/update-lab/images/R3/linux-x64/update_lab_launcher --image /srv/update-lab/images/R3 --install /tmp/lab-install --profile /tmp/lab-profile --provider CLIENT_UID
```

Сервис требуется для проверки обновлений и догрузки. Для автономной установки достаточно каталога образа, launcher и полного исполняемого файла своей платформы. При передаче Linux-бинарников через Windows сохраните право запуска launcher (`chmod +x`). Launcher выставляет права установленному приложению.

Для ручной проверки начните с R0 в свежем профиле. Выберите русский, дождитесь переключения и вернитесь на English. Теперь выберите R3. После перезапуска у прежних клонов появится S1. Повторный выбор русского сработает без загрузки. Кнопка проверки сбоя запускает кандидата E2 и возвращает рабочую E1. Для проверки докачки выберите медленное соединение, начните первую загрузку Deutsch и закройте окно во время прогресса. Запустите приложение с тем же профилем.

Чтобы воспроизвести появление обновления спустя время, опубликуйте тот же комплект бинарников с `-Through 1`, установите R1 и закройте приложение. Повторите публикацию в тот же `-Store` с `-Through 3`. При следующем старте R1 получит от работающего сервиса предложение R3/E1 и оставшийся объём загрузки.

## Выпуски и состав дистилляции

| Поставка | Изменение | Исполняемый файл |
| --- | --- | --- |
| R0 | English встроен. Русский доступен по запросу | E0 |
| R1 | Изменены английское и русское приветствия | E0 |
| R2 | Добавлен загружаемый Deutsch | E0 |
| R3 | Префаб получает TextObject/S1, обновлена русская строка готовности | E1 |

E2 — отдельный намеренно неисправный кандидат для проверки отката. При выборе R0/R1 с активным Deutsch включается English. Неизменённые пользовательские клоны получают S1 штатной загрузкой через `Obj::origin_id()`. Их ObjId, пользовательский S0 и явный S1 override сохраняются при переходе назад и вперёд.

`DistillRelease` в `supply_builder.cpp` задаёт список загружаемых корней. Каждый `LocalizationState` хранит код и ссылки на отдельные `LocalizedString` со стабильными ObjId. Дистиллятор помещает корень и объекты его области владения в один раздел. Все корни без пометки остаются в полном встроенном состоянии. Адрес объекта и его слоёв одинаков в обоих случаях. Для видимого прогресса у загружаемых языков в демонстрационном графе есть стабильные 384 КиБ данных. Изменение одной строки порождает дельту соответствующего слоя.

Пример каталога сервиса, сокращённого до одной версии.

```text
catalog.bin
images/
  R3/
    release.bin
    full.ats
    full/<ObjId>/<ClassId>/<S>
    full/<ObjId>/.scope
    downloads/
      ru.ats
      de.ats
    windows-x64/
      update_lab.exe
      update_lab_launcher.exe
      update.ats
      telemetry/
    linux-x64/
      update_lab
      update_lab_launcher
      update.ats
      telemetry/
    deltas/from-R2/
      state.ats
      state/<ObjId>/<ClassId>/<S>
      state/operations.bin
      downloads/ru.ats
fixtures/<platform>/broken.ats
```

Каждый `images/Rn` самодостаточен для новой установки. В `full/` лежит по файлу на S-слой, в `full.ats` — то же базовое состояние для доставки одним файлом. Каталог `downloads/` содержит полную копию каждого опционального пакета этой версии. При обычной установке эти файлы остаются у поставщика. В `deltas/from-Rm/` помещаются соседние переходы в Rn, включая обратные. `operations.bin` описывает удаления, tombstones и области владения для распакованного представления. Упакованная дельта содержит все эти данные внутри одного файла.

Полный PE или ELF лежит рядом с launcher. Его сжатая копия `update.ats` предназначена для сетевого обновления. В `telemetry/` упаковщик кладёт символы и предоставленные сборкой каталоги декодирования SDK. Их можно передать через `--<platform>-e<N>-symbols` и `--<platform>-e<N>-telemetry`. Эти файлы остаются у издателя при сетевом обновлении.

`release.bin` описывает конкретный образ, его E, корни языков, ревизии и ID пакетов. Сервисный `catalog.bin` строится упаковщиком и публикуется атомарно после записи файлов. Клиент получает ответ на запрос к сервису. Сервис перечитывает каталог при запросе, поэтому уже запущенный поставщик видит допубликованные версии.

## Что приложение запрашивает у сервиса

При обычном старте устройство отправляет `resolve-update` через Æther. Запрос содержит платформу, текущие R и E, цель (последняя либо конкретная R), выбранный язык, установленные опциональные пакеты с ревизиями и уже принятые байты компонентов. Ответ содержит доступные версии для этой платформы, целевую R/E, ID исполняемого файла при замене, цепочки состояния и ресурсов, размеры компонентов, сумму и остаток байтов полезной нагрузки. Служебный трафик Æther в оценку не входит.

Например, на R0/E0 пользователь скачал русский и вернулся на английский. Когда опубликована R3, в план входят следующие компоненты.

1. Три соседние дельты базового состояния R0→R1→R2→R3.
2. Две дельты установленного русского. Первая меняет приветствие на переходе R0→R1. Вторая меняет строку готовности на переходе R2→R3. На R2 русские данные сохраняют ревизию 1.
3. Один полный E1 целевой платформы. Deutsch останется доступен для отдельного запроса.

При первом выборе нового языка сервис включает его полный пакет целевой версии. При переходе установленного ресурса во встроенное состояние используется новая база. Пропуск обязательной дельты даёт ошибку с её ID. Ответ при запуске показывает предложение в окне. Выбор строки версии применяет обновление. Параметр `--latest` применяет последнюю доступную версию из командной строки. После разрешения цель фиксируется на время закачки.

## Состояние устройства

| Путь | Владелец и содержимое |
| --- | --- |
| `profile/user.bin` | Native USER, активные R и язык, заметка, ObjId клонов и пользовательские слои |
| `profile/local/user.bin` | Native LOCAL, имя устройства, положение и размер окна, ограничение скорости |
| `profile/local/installed.bin` | Установленный образ и ревизии всех установленных опциональных ресурсов |
| `profile/local/transfer/user.bin` | Native DownloadNode, намерение, прогресс, готовность и ошибка |
| `profile/local/packages/` | Полные и восстановленные состояния, дельты, загруженные компоненты, файлы `.part` |
| `profile/local/prepared-plan.bin` | Зафиксированный план для завершения активации и автономного пробного запуска |
| `profile/local/download-identity/` | Идентичность клиента Æther устройства |
| `installation/` | Журнал launcher, слоты EXE и снимок для отката |

Загрузка идёт в рабочем потоке. Прогресс, готовность и ошибка поступают в модель как Events объекта DownloadNode. Блок сначала записывается и сбрасывается на диск, затем сохраняется прогресс. При рестарте загрузчик усекает незакоммиченный хвост и продолжает с подтверждённой позиции. Старый текст остаётся виден во время загрузки. После готовности базы, всех установленных ресурсов и исполняемого файла модель сохраняет язык и R одним UserChanged и публикует готовый интерфейс. При прерывании между заменами файлов USER и локального инвентаря приложение завершает подготовленную активацию до первой публикации интерфейса.

При замене EXE launcher сохраняет USER, LOCAL и перечень установленных ресурсов. Кандидат запускается из другого слота и подтверждает исправность после применения состояния и потребления публикации UI. Сбой, таймаут или прерванный trial восстанавливают снимок и предыдущий слот. Кеш загруженных байтов остаётся на устройстве.

Export и Import переносят один сжатый файл USER. Целевая установка сохраняет собственные настройки, идентичность, платформенный исполняемый файл и инвентарь ресурсов. Если для импортированных R и языка нужны компоненты, их получает клиент на целевом устройстве.

## Упаковщик и проверки

```text
update_lab_pack full user.bin 0 R0.full.ats
update_lab_pack delta before.bin after.bin 0 1 R0-R1.delta.ats
update_lab_pack apply before.bin R0-R1.delta.ats 0 after.bin
update_lab_pack inspect R0-R1.delta.ats
```

Метаданные пакета занимают 24 байта. Дальше идёт Zstandard magicless frame с отключённой контрольной суммой. Прикладной сигнатуры и дайджестов у пакета нет. Используются level 19 для native-состояния и дельт, level 9 для EXE, окно до 1 МиБ. На графе из 20 000 объектов распаковка Zstd 19 заняла 1,86 мс. Измеренный прирост EXE от оптимизированного декодера обычной LZMA1 составил 9,50 КиБ, из них 9,34 КиБ машинного кода. Методика и сравнение размеров, памяти и скорости приведены в [анализе компрессоров](update_lab_compression.md).

`update_lab_state_test` проверяет native-слои, соответствие дельт полному образу, поведение S1/origin, формат и разрешение цепочек. `tools/test_update_lab.py` проверяет отдельные процессы Windows и Linux, `tools/test_update_lab_cloud.py` — доставку через реального Æther-клиента. Параметр приложения `--native-smoke` упражняет реальные Win32/GTK controls и UI mirror.
