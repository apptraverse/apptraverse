# UpdateLab

UpdateLab — автономный пример AppTraverse для Windows x64 и Linux x64. Одно нативное окно показывает перевод, список языков, доступные версии, пользовательскую заметку, клоны префаба и прогресс загрузки. За доставку состояния, переводов и исполняемого файла отвечает отдельный клиент Æther.

## Простое приложение жизненного цикла для Windows

В окне два языка и список версий. English входит в R0. При выборе русского клиент получает реальный пакет через Æther и добавляет искусственную задержку из расчёта 64 КиБ/с. Во время загрузки английский остаётся активным. После применения всего пакета одновременно переключаются текст, подписи и выбранный язык. При закрытии окна прогресс сохраняется и активная загрузка продолжается со следующего блока после запуска. Кнопка «Пауза» сохраняет подтверждённые блоки и меняется на «Продолжить». Явная пауза сохраняется при перезапуске.

Во время скачивания доступны выбор языка, список версий и проверка обновлений. Проверка каталога идёт параллельно. Выбор другого языка или версии задаёт новую цель загрузки, а принятые блоки первой цели остаются в кеше.

```powershell
./tools/build_update_lab.ps1 -BuildDirectory build/win-lifecycle -BuildOnly
./tools/start_update_lifecycle.ps1 -Provider a1ea11f9-68b5-4524-adbb-34ff05e595cb -App lifecycle-pause-demo
```

Скрипт устанавливает полный локальный R0/E0 при первом запуске. Следующие запуски открывают состояние того же устройства. Укажите `-DeviceRoot` для отдельной установки или `-App lifecycle-demo-alt` для второго приложения.

- **Версия** сразу переключает на выбранный выпуск. Назад идут обратные дельты. Если версии нужен другой EXE, приложение перезапускается через launcher.
- **Проверить обновления** запрашивает у сервиса актуальную версию. На R0 основной каталог предлагает R3/E1 и показывает оставшийся объём для каждого режима.
- **Обновить только .bin** применяет цепочку native-состояний и дельты уже установленных языков, сохраняя работающий E0. После R0→R3 в окне отображается R3/E0. Данные всех четырёх демовыпусков совместимы с E0 и E1.
- **Обновить с EXE** применяет то же целевое состояние и заменяет приложение через пробный запуск. При сбое сохраняется предыдущая рабочая установка. Если состояние уже R3, этот режим получает только E1.

На тестовой VM `aether-test-server` сервис `apptraverse-lifecycle` обслуживает каталоги через один UID. `lifecycle-pause-demo` содержит сборку с паузой до R3. Первоначальные `lifecycle-demo` и `lifecycle-demo-alt` доступны на R3 и R1 соответственно. На запросе ключами служат ID приложения и ID компонента. Профили, метаданные и кеши разных приложений изолированы. [Публикация и развёртывание сервиса](../services/update_lifecycle/README.md). [Результаты проверок](validation/update-lab-lifecycle-2026-11-23.md).

## Запуск классического UpdateLab

На Windows из корня репозитория, Visual Studio 2022/v143, Debug.

```powershell
./tools/build_update_lab.ps1
./tools/start_update_lab.ps1 -InitialRelease 1
```

Первый запуск ставит выбранную поставку из полного образа. Следующие запуски используют активный слот той же установки. Скрипт поднимает сервисный клиент и передаёт приложению его UID. Для файлового теста укажите `-FileSource`. Параметры `-Profile` и `-Installation` позволяют создать отдельное устройство. `-StoreDirectory` выбирает каталог поставок.

Для общей поставки сначала соберите Linux-бинарники в WSL, затем передайте их Windows-упаковщику.

```sh
bash tools/build_update_lab_linux.sh /home/nickc/update-lab-build
```

```powershell
./tools/build_update_lab.ps1 -LinuxBinaries '\\wsl.localhost\Ubuntu\home\nickc\update-lab-build\update-lab-package'
```

Один клиент обслуживает обе платформы. Windows-скрипт пишет в `artifacts/update-lab/lzma1-releases`, Linux-скрипт — в `artifacts/update-lab/lzma1-releases-linux`. У Windows-скрипта есть параметры `-Store` и `-Through`, у Linux-скрипта путь переопределяет переменная `UPDATE_LAB_STORE`. Имена компонентов привязаны к версиям. Для пересобранного прототипа с другим содержимым под теми же номерами укажите новый каталог.

Пример установки сразу на R3 с последующей работой через Æther.

```sh
update_lab_provider --store /srv/update-lab --profile /var/tmp/component-client --endpoint-file /var/tmp/endpoint
/srv/update-lab/images/R3/linux-x64/update_lab_launcher --image /srv/update-lab/images/R3 --install /tmp/lab-install --profile /tmp/lab-profile --provider CLIENT_UID
```

Сервис требуется для проверки обновлений и догрузки. Для автономной установки достаточно каталога образа, launcher и полного исполняемого файла своей платформы. При передаче Linux-бинарников через Windows сохраните право запуска launcher (`chmod +x`). Launcher выставляет права установленному приложению.

Для ручной проверки начните с R0 в свежем профиле. Выберите русский, дождитесь переключения и вернитесь на English. Теперь выберите R3. После перезапуска у прежних клонов появится S1. Повторный выбор русского сработает без загрузки. Кнопка проверки сбоя запускает кандидата E2 и возвращает рабочую E1. Для проверки докачки выберите медленное соединение, начните первую загрузку Deutsch и закройте окно во время прогресса. Запустите приложение с тем же профилем.

Чтобы воспроизвести появление обновления спустя время, опубликуйте тот же комплект бинарников с `-Through 1`, установите R1 и закройте приложение. Повторите публикацию в тот же `-Store` с `-Through 3`. При следующем старте R1 получит от работающего сервиса предложение R3/E1 и оставшийся объём загрузки.

## Выпуски и состав дистилляции

| Поставка | Изменение | Исполняемый файл |
| --- | --- | --- |
| R0 | English встроен. Русский доступен по запросу | E0 |
| R1 | Изменены английское и русское приветствия | E0 |
| R2 | Добавлен загружаемый Deutsch | E0 |
| R3 | Префаб получает TextObject/S1, обновлена русская строка готовности | E1 |

E2 — отдельный намеренно неисправный кандидат для проверки отката. При выборе R0/R1 с активным Deutsch включается English. Неизменённые пользовательские клоны получают S1 штатной загрузкой через `Obj::origin_id()`. Их ObjId, пользовательский S0 и явный S1 override сохраняются при переходе назад и вперёд.

`DistillRelease` в `supply_builder.cpp` задаёт список загружаемых корней. Каждый `LocalizationState` хранит код и ссылки на отдельные `LocalizedString` со стабильными ObjId. Дистиллятор помещает корень и объекты его области владения в один раздел. Все корни без пометки остаются в полном встроенном состоянии. Адрес объекта и его слоёв одинаков в обоих случаях. Для видимого прогресса у загружаемых языков в демонстрационном графе есть стабильные 384 КиБ данных. Изменение одной строки порождает дельту соответствующего слоя.

Пример каталога сервиса, сокращённого до одной версии.

```text
catalog.bin
images/
  R3/
    release.bin
    full.ats
    full/<ObjId>/<ClassId>/<S>
    full/<ObjId>/.scope
    downloads/
      ru.ats
      de.ats
    windows-x64/
      update_lab.exe
      update_lab_launcher.exe
      update.ats
      telemetry/
    linux-x64/
      update_lab
      update_lab_launcher
      update.ats
      telemetry/
    deltas/from-R2/
      state.ats
      state/<ObjId>/<ClassId>/<S>
      state/operations.bin
      downloads/ru.ats
fixtures/<platform>/broken.ats
```

Каждый `images/Rn` самодостаточен для новой установки. В `full/` лежит по файлу на S-слой, в `full.ats` — то же базовое состояние для доставки одним файлом. Каталог `downloads/` содержит полную копию каждого опционального пакета этой версии. При обычной установке эти файлы остаются у поставщика. В `deltas/from-Rm/` помещаются соседние переходы в Rn, включая обратные. `operations.bin` описывает удаления, tombstones и области владения для распакованного представления. Упакованная дельта содержит все эти данные внутри одного файла.

Полный PE или ELF лежит рядом с launcher. Его сжатая копия `update.ats` предназначена для сетевого обновления. В `telemetry/` упаковщик кладёт символы и предоставленные сборкой каталоги декодирования SDK. Их можно передать через `--<platform>-e<N>-symbols` и `--<platform>-e<N>-telemetry`. Эти файлы остаются у издателя при сетевом обновлении.

`release.bin` описывает конкретный образ, его E, корни языков, ревизии и ID пакетов. Сервисный `catalog.bin` строится упаковщиком и публикуется атомарно после записи файлов. Клиент получает ответ на запрос к сервису. Сервис перечитывает каталог при запросе, поэтому уже запущенный поставщик видит допубликованные версии.

## Что приложение запрашивает у сервиса

При обычном старте устройство отправляет `resolve-update` через Æther. Запрос содержит платформу, текущие R и E, цель (последняя либо конкретная R), выбранный язык, установленные опциональные пакеты с ревизиями и уже принятые байты компонентов. Ответ содержит доступные версии для этой платформы, целевую R/E, ID исполняемого файла при замене, цепочки состояния и ресурсов, размеры компонентов, сумму и остаток байтов полезной нагрузки. Служебный трафик Æther в оценку не входит.

Например, на R0/E0 пользователь скачал русский и вернулся на английский. Когда опубликована R3, в план входят следующие компоненты.

1. Три соседние дельты базового состояния R0→R1→R2→R3.
2. Две дельты установленного русского. Первая меняет приветствие на переходе R0→R1. Вторая меняет строку готовности на переходе R2→R3. На R2 русские данные сохраняют ревизию 1.
3. Один полный E1 целевой платформы. Deutsch останется доступен для отдельного запроса.

При первом выборе нового языка сервис включает его полный пакет целевой версии. При переходе установленного ресурса во встроенное состояние используется новая база. Пропуск обязательной дельты даёт ошибку с её ID. Ответ при запуске показывает предложение в окне. Выбор строки версии применяет обновление. Параметр `--latest` применяет последнюю доступную версию из командной строки. После разрешения цель фиксируется на время закачки.

## Состояние устройства

| Путь | Владелец и содержимое |
| --- | --- |
| `profile/user.bin` | Native USER, активные R и язык, заметка, ObjId клонов и пользовательские слои |
| `profile/local/user.bin` | Native LOCAL, имя устройства, положение и размер окна, ограничение скорости |
| `profile/local/installed.bin` | Установленный образ и ревизии всех установленных опциональных ресурсов |
| `profile/local/transfer/user.bin` | Native DownloadNode, намерение, прогресс, готовность и ошибка |
| `profile/local/packages-lzma1/` | Полученные пакеты, восстановленные native-состояния (`*.native`), незавершённые файлы `.part` |
| `profile/local/packages-lzma1/prepared-plan.bin` | Зафиксированный план для завершения активации и автономного пробного запуска |
| `profile/local/download-identity/` | Идентичность клиента Æther устройства |
| `installation/` | Журнал launcher, слоты EXE и снимок для отката |

Загрузка идёт в рабочем потоке. Прогресс, готовность и ошибка поступают в модель как Events объекта DownloadNode. Блок сначала записывается и сбрасывается на диск, затем сохраняется прогресс. При рестарте загрузчик усекает незакоммиченный хвост и продолжает с подтверждённой позиции. Старый текст остаётся виден во время загрузки. После готовности базы, всех установленных ресурсов и исполняемого файла модель сохраняет язык и R одним UserChanged и публикует готовый интерфейс. При прерывании между заменами файлов USER и локального инвентаря приложение завершает подготовленную активацию до первой публикации интерфейса.

При замене EXE launcher сохраняет USER, LOCAL и перечень установленных ресурсов. Кандидат запускается из другого слота и подтверждает исправность после применения состояния и потребления публикации UI. Сбой, таймаут или прерванный trial восстанавливают снимок и предыдущий слот. Кеш загруженных байтов остаётся на устройстве.

Export и Import переносят один сжатый файл USER. Целевая установка сохраняет собственные настройки, идентичность, платформенный исполняемый файл и инвентарь ресурсов. Если для импортированных R и языка нужны компоненты, их получает клиент на целевом устройстве.

## Упаковщик и проверки

```text
update_lab_pack full user.bin 0 R0.full.ats
update_lab_pack delta before.bin after.bin 0 1 R0-R1.delta.ats
update_lab_pack apply before.bin R0-R1.delta.ats 0 after.bin
update_lab_pack inspect R0-R1.delta.ats
```

Команда `update_lab_provider publish` запускается на машине сервиса. Она собирает каталоги слоёв, вычисляет прямые и обратные дельты между соседними R, сжимает содержимое и в конце атомарно публикует `catalog.bin`. Доставка читает уже подготовленные байты. Обе сборочные команды из раздела запуска вызывают этот режим. Команда `update_lab_pack publish` использует ту же реализацию.

Все полные состояния, дельты, языки и обновления EXE используют однопоточный энкодер LZMA1 из 7-Zip SDK. Выбран максимальный уровень 9 и максимальная длина быстрого поиска 273 байта. Энкодер уменьшает словарь под размер входа. После прежних 24 байт метаданных идут 5 байт параметров декодера и один raw-поток LZMA1 с маркером окончания. У пакета нет magic и контрольной суммы. Клиент применяет цепочку дельт к native-состоянию и сохраняет результат в локальном кеше. Максимальное сжатие на устройстве требуется только при явном экспорте USER. [Анализ компрессоров и размер декодера](update_lab_compression.md).

**Переход с Zstd.** Сервис использует формат каталога 4 и протокол доставки 2. Каталоги LZMA1 формата 3 читаются для совместимости. Публикуйте его в отдельный каталог. При переходе со старой установки запустите новый launcher с `--seed <новый E0>`, отдельным `--install`, прежним `--profile` и новым `--provider` или `--store`. Для этого перехода E0 берётся из нового R0. Native USER и LOCAL сохраняются. Клиент получает совместимые пакеты базы и установленных языков у нового поставщика. Частичные старые потоки остаются в старом кеше. Для ранее экспортированного USER предусмотрена однократная конвертация на десктопе с модулем Python `zstandard`.

```powershell
python tools/convert_update_lab_user.py old-user.ats new-user.ats --packer build/win-update-lab/examples/update_lab/Debug/update_lab_pack.exe
```

`update_lab_state_test` проверяет native-слои, соответствие дельт полному образу, поведение S1/origin, формат и разрешение цепочек. `tools/test_update_lab.py` проверяет отдельные процессы Windows и Linux, `tools/test_update_lab_cloud.py` — доставку через реального Æther-клиента. Параметр приложения `--native-smoke` упражняет реальные Win32/GTK controls и UI mirror.

[Проверки LZMA1 на Windows/Linux](validation/update-lab-lzma1-2026-11-23.md). [Результаты предыдущей поставки](validation/update-lab-2026-11-22.md).


## Предлагаемый протокол удалённой публикации

Клиенты доставки получают план и блоки через Æther. Действующий скрипт публикации использует административный SSH-доступ. Следующая схема описывает вариант отдельного протокола публикации через Æther. Один и тот же сервис хранит полные образы каждой R и соседние прямые и обратные дельты. Десктопу достаточно изменять один параметр сборочного профиля.

| Режим | Что передаёт скрипт после сборки | Что делает сервис |
| --- | --- | --- |
| `deltaProducer=service` (по умолчанию) | Дистиллированное полное состояние, описания встроенных и догружаемых корней, изменившиеся платформенные бинарники, символы | Сравнивает с сохранённой родительской R по ObjId/ClassId/S, вычисляет обе дельты. Простой издатель, больше входящего трафика |
| `deltaProducer=desktop` | Скрипт берёт точную родительскую R и передаёт native-дельту. По запросу добавляет полный новый ресурс, отсутствующую базу и платформенные файлы | Применяет дельту к родителю, сохраняет полный образ для чистой установки, строит обратную дельту из обоих состояний. Меньше трафика при малом изменении, издателю нужна база |
| `deltaProducer=auto` | Выбирает режим для каждого компонента по списку известных сервису ревизий и наличию соответствующей локальной базы | Подтверждает выбор в плане загрузки. Для первого выпуска или нового языка запрашивает полное состояние |

Пример профиля публикации для скрипта. Имена полей относятся к предложенному протоколу.

```yaml
channel: stable
deltaProducer: service       # service | desktop | auto
signingProfile: desktop-release
rollback:
  device: on-failed-health
  channel: explicit
```

Во всех режимах итоговые LZMA1-файлы сжимает сервис. Для EXE политика по умолчанию — передать полные уже подписанные байты один раз для новой пары (платформа, E). Ревизию E можно переиспользовать в следующих образах. Для Windows скрипт подписывает PE до загрузки, для Linux можно согласовать отдельную подпись ELF. Закрытый ключ остаётся на машине подписания или в её хранилище ключей. Сервис проверяет подпись доверенного издателя до публикации. Launcher по той же политике проверяет распакованный EXE или пару ELF/подпись перед пробным запуском. Подпись ELF входит в список компонентов плана для Linux. Подпись приложения и вход издателя в Æther решают отдельные задачи. Формат пакета остаётся прежним. [Microsoft SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool).

| Сообщение | Результат |
| --- | --- |
| `BeginPublish(requestId, channel, expectedGeneration, release, parent, deltaProducer, inventory)` | Сервис проверяет право издателя на канал и резервирует черновик. Возвращает `uploadId`, режим по компонентам, какие файлы нужны и сколько байтов уже принято |
| `PutPart(uploadId, artifactId, offset, bytes)`, `PublishStatus(uploadId)` | Устойчивый подтверждённый offset для каждого файла. Скрипт продолжает после обрыва. Повтор того же диапазона идемпотентен |
| `Prepare(uploadId)` | Запускает фоновую подготовку. Сервис собирает полную поставку каждой платформы, проверяет подписи и применимость прямого и обратного переходов. PublishStatus сообщает стадию, ошибку либо готовый манифест с окончательными размерами |
| `Commit(uploadId, expectedGeneration)` | После завершения записи файлов атомарно переключает указатель канала (целевая R, поколение манифеста). Повтор возвращает исходный результат. При конфликте поколения издатель получает актуальную голову для пересмотра публикации |
| `Abort(uploadId)` | Закрывает незавершённую публикацию. Устройства всё это время продолжают получать прежнюю голову |
| `SetChannelHead(channel, targetR, expectedGeneration, reason)` | Переключает канал на сохранённую подготовленную R и увеличивает поколение. История и полные образы остаются доступными |

**Откат устройства и канала.** Устройство уже подтверждает запуск кандидата и восстанавливает предыдущий EXE, USER и LOCAL при неудаче. Для нового протокола стоит запоминать неудачный кандидат вместе с поколением, чтобы следующий запуск не повторял его автоматически. Массовый откат выполняется через `SetChannelHead`. Например, после переключения R3→R1 новая установка сразу получает полный R1. Устройство на R3 получает R3→R2→R1, подходящий E и изменения установленных языков. USER мигрирует относительно текущего состояния, настройки LOCAL остаются на устройстве. Поколение манифеста растёт даже при движении R назад.

Для постепенного развёртывания можно добавить каналы `canary` и `stable`: сначала направить тестовые устройства на новый образ, затем одним переключением продвинуть тот же выпуск в основной канал. Место вычисления дельт выбирается независимо.
