# Выбор компрессора для UpdateLab

Выбран **Zstandard 1.5.7: level 19, windowLog 20 для состояний и дельт**.
Для больших blob-компонентов (EXE и языковые пакеты) используется level 9:
его существенно быстрее собирать, а распаковка остаётся быстрой. Checksum frame
отключён. У текущих пакетов нет собственной файловой сигнатуры; Zstd frame
также magicless. Табличные замеры ниже сделаны до этой правки со стандартными
Zstd frames: их сжатый размер включает четырёхбайтовый magic. Старые измеренные
размеры пакетов включали также прежнюю строку `ATSTATE1`; эти числа сохранены
как исторический результат, не как размер текущих файлов.

## Методика

Замеры выполнены на этом Windows x64 хосте, Intel Family 6 Model 154, Python
3.11.9, python-zstandard 0.25.0 с libzstd 1.5.7, Brotli 1.2.0. Скрипт:
`tools/benchmark_update_compression.py`. Для каждого кодека — медиана трёх
серий; память измеряется в отдельных процессах как прирост пикового working set
ОС относительно процесса с уже прочитанным входом. Это включает выходные
буферы и поведение Python binding/allocator, а не только память алгоритма.

Корпус: настоящие полные native-образы с локализациями R0 (1 034 B), R3 (1 461 B),
USER после прохода версий, отката и переноса (2 805 B), а также корректный
native-граф из 20 000 TextObject с origin,
разными именами и текстами на трёх языках (2 022 403 B). Последний граф создан
`update_lab_pack corpus`: это масштабированный тестовый набор, не реальные
пользовательские данные. Демонстрационный случайный payload языковых пакетов
в замеры состояний не включён.

## Результат на графе 20 000 объектов

| Кодек | Сжатый размер, B | Сжатие, ms | Распаковка, ms | Доп. пик encoder, MiB | Доп. пик decoder, MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| Zstd 9, окно 1 MiB | 89 941 | 28.59 | 1.855 | 10.39 | 2.00 |
| Zstd 15, окно 1 MiB | 89 894 | 45.00 | 1.489 | 16.37 | 2.00 |
| **Zstd 19, окно 1 MiB** | **76 897** | **1 260.95** | **1.864** | **16.91** | **2.00** |
| LZ4 HC 12 | 255 048 | 206.43 | 1.606 | 0.57 | 3.95 |
| LZMA2 preset 9, словарь 1 MiB | 45 336 | 669.56 | 7.919 | 12.64 | 5.03 |
| LZMA2 preset 9, словарь 8 MiB | 45 456 | 691.45 | 7.191 | 34.14 | 5.95 |
| Raw Deflate 9 | 140 053 | 162.88 | 3.131 | 0.57 | 3.90 |
| Bzip2 9 | 55 771 | 125.70 | 25.591 | 6.46 | 7.44 |
| Brotli 11, окно 1 MiB | 86 553 | 2 980.85 | 3.505 | 21.20 | 5.12 |

Здесь Zstd 19 даёт на 14.5% меньше байт, чем Zstd 9, ценой долгой офлайн-сборки.
LZMA2 с малым словарём сжимает лучше, но распаковывается в 4.25 раза медленнее.
LZMA2 с 8 MiB словарём не улучшил размер этого корпуса. Zstd 15 почти не
выиграл размер у 9. LZ4 потребовал в 3.32 раза больше байт, чем Zstd 19.
Это результаты конкретного корпуса; небольшие различия скорости между быстрыми
кодеками не следует переносить на другие устройства.

Brotli 11 с тем же окном дал больший файл, более долгую распаковку и больший
измеренный пик памяти, чем Zstd 19. Для него использован `lgwin=20` через
[официальный Python wrapper](https://github.com/google/brotli/blob/master/python/brotli.py).

На маленьких реальных состояниях Zstd 19 дал 581 B для R0, 802 B для R3 и 586 B
для USER. Это размер стандартного frame в исходном замере; прежний внешний
заголовок добавлял 36 B. Сейчас метаданные занимают 24 B, а frame короче на 4 B.
Дельты дополнительно сокращают канонические входные данные до изменённых слоёв:
компрессор не заменяет вычисление графовой дельты.
Например, R2→R3 занимает 155 B вместе с заголовком, полный R3 — 838 B.
На R0→R1, где меняются массивы перевода обоих языков, дельта почти равна полному
образу: 614 против 626 B для R1. Дельта не гарантирует выигрыш на крошечных графах.

## Размер кода декодера

Отдельно измерен Zstd 1.5.7, Windows x64, MSVC 19.44/v143: минимальный C EXE,
вызывающий `ZSTD_decompress`, минус такой же EXE без декодера. Компрессор не
линковался; PDB и размер внешнего CRT DLL не включены. Это приращение бинарника,
включая небольшой вызывающий код и дополнительные импорты, а не размер `.lib`.

| Конфигурация decoder probe | Машинный код `.text`, KiB | Константы/строки `.rdata`, KiB | Прирост EXE на диске, KiB |
| --- | ---: | ---: | ---: |
| Существующая Debug-библиотека UpdateLab, без оптимизации | 132.78 | 28.59 | 170.50 |
| Отдельная сборка декодера на размер, `/O1 /Ob1 /Gy /Gw`, linker `/OPT:REF /OPT:ICF` | 58.61 | 4.37 | 64.00 |

Размеры секций взяты из PE VirtualSize, размер файла — фактическая разница;
в EXE также входят unwind metadata и файловое выравнивание. В обоих случаях
ASM и legacy frames отключены. Для Debug использована уже собранная библиотека
примера с `/MDd`; size probe использует `/MD`, `NDEBUG` и только common/decompress
исходники. Оба probe успешно распаковали встроенный frame. Это отдельный замер
размера C-декодера, не Release-сборка приложения и не повторный замер скорости.

Итого ориентир для отдельного оптимизированного декодера — **около 64 KiB в EXE**.
Текущее приложение также использует компрессор для экспорта USER и упаковки
восстановленного состояния; его полная добавка Zstd этим числом не описывается.
Исходники probe, link maps, парсер PE и результаты находятся в
`artifacts/update-lab/code-footprint/`, численные данные — `results.json`.

## Дополнение: обычный LZMA1

Измерен отдельный C decoder `LzmaDec.c` из официального 7-Zip SDK 26.06,
commit `d3296e39e1f1f92c7b41c0c3848e65640428d42d`, без LZMA2, XZ, ASM,
потоков и encoder. Методика footprint та же, что для Zstd выше.

| Decoder | `.text`, KiB | `.rdata`, KiB | Прирост EXE, KiB |
| --- | ---: | ---: | ---: |
| LZMA1 C, Debug | 22.22 | 0.21 | 23.00 |
| LZMA1 C, `/O1 /Ob1 /Gy /Gw`, `/OPT:REF /OPT:ICF` | 9.34 | 0.45 | 9.50 |

Для `lc=3, lp=0, pb=2` allocator probe однократного `LzmaDecode` зафиксировал
16 256 B под вероятности, структура `CLzmaDec` — 128 B. Этот API использует
весь заранее выделенный выходной буфер как словарь (`p.dic = dest`); отдельно
1 MiB истории в этом режиме не выделяется. Выходной буфер, входные данные,
стек и накладные расходы allocator — отдельные расходы. Streaming API требует
собственного словаря. Поэтому прежний пик Python/XZ нельзя приписывать этому
native C one-call decoder.
([Исходник SDK](https://github.com/ip7z/7zip/blob/26.06/C/LzmaDec.c))

Дополнительный прогон Python/liblzma с raw LZMA1, preset 9, dictionary 1 MiB:
на графе 2 022 403 B результат 45 285 B, сжатие 724.65 ms, распаковка 7.632 ms.
Это скорость liblzma binding, не измерение скорости SDK C decoder. Native R0,
R3 и USER дали 546, 756 и 568 B соответственно. Все четыре round-trip прошли;
raw stream не имеет checksum. Данные: `artifacts/update-lab/compression-lzma1.json`;
добавлен выбор `--codec lzma1-1` в benchmark tool. Footprint/allocator probes:
`artifacts/update-lab/code-footprint/lzma-results.json`, `lzma_memory.c`.

LZMA2 не требует многопоточности: число потоков — отдельный режим. Для данного
single-shot прототипа обычный LZMA1 достаточен. По компактности native decoder
он существенно выгоднее Zstd; прежний выбор Zstd учитывал прежде всего скорость
распаковки. Runtime прототипа пока остаётся на Zstd, смена codec не выполнена.
([Руководство XZ](https://tukaani.org/xz/man/xz.1.html))

## Память декодера

У измеренного libzstd контекст однократного декодирования занимает **95 968 B**.
Реализация использует `ZSTD_decompressDCtx` с явно заданным magicless format
в заранее выделенный буфер с известным размером. Для однократного режима
документация описывает постоянную память контекста;
потоковому декодеру дополнительно нужно окно истории.
([Документация libzstd о памяти](https://github.com/facebook/zstd/wiki/Using-libzstd-in-a-memory-constrained-environment))

Окно 1 MiB — ограничение истории, не лимит RSS приложения. Текущий загрузчик
также держит сжатый компонент, распакованные native-байты и затем объектный граф.
Для большого EXE главным буфером является сам распакованный файл. Общий лимит
компонента в примере — 256 MiB; это отдельный параметр формата/загрузчика.

У LZMA2 размер словаря влияет и на память распаковки; поэтому сравнивались
отдельно 1 и 8 MiB, а не только стандартный высокий preset с большим словарём.
([Руководство XZ](https://tukaani.org/xz/man/xz.1.html))
Пики Python-процессов в таблице включают временные выходные буферы: их нельзя
трактовать как точные размеры C++ decoder workspace.

Для прототипа приоритет — быстрая распаковка на устройстве и ограниченное окно.
Если приоритетом станет минимальный сетевой размер, LZMA2/1 MiB остаётся
измеренным вариантом. Если ограничена память упаковщика, Zstd 9 или LZ4 требуют
отдельного выбора по допустимому размеру результата.

Воспроизведение:

```powershell
python -m pip install -r tools/update_lab_benchmark_requirements.txt
update_lab_pack corpus artifacts/update-lab/scaled-20000.native.bin
python tools/benchmark_update_compression.py --input R0.native.bin R3.native.bin scaled-20000.native.bin user.bin --output results.json
```

Полные численные результаты текущего прогона:
`artifacts/update-lab/compression-native-final.json`. C++ использует те же level/window
через [публичные параметры libzstd 1.5.7](https://github.com/facebook/zstd/blob/v1.5.7/lib/zstd.h).
